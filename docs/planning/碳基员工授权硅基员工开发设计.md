# 碳基员工授权硅基员工开发设计

**状态**：待评审
**适用版本**：SEP 企业组织端
**目标入口**：`/members` 碳基员工（企业成员）页面
**关联现有能力**：`EmployeeGrant`、企业成员管理、订阅/雇佣关系、`/subscriptions/:id/grants/batch`

## 1. 背景与目标

当前系统已经支持企业管理员在“雇佣关系”页面中，把某一个硅基员工授权给成员或部门。授权记录落在 `EmployeeGrant`，支持直接授权、部门授权、长期/限时授权和批量授权。

当前入口与用户工作方式不一致：管理员在碳基员工列表中先找到“姚瑞泉”，通常希望直接回答“给他哪些硅基员工”，却必须跳到每个硅基员工的雇佣关系详情页逐个操作。本需求把授权入口补到碳基员工页面，支持：

1. 面向单个碳基员工，选择一个或多个已雇佣的硅基员工并授权。
2. 单选和多选使用同一套事务接口；选择 1 个时即为单个授权，选择多个时为批量授权。
3. 查看该成员当前的直接授权、部门覆盖情况、授权有效期，并可收回直接授权。
4. 保持现有“硅基员工 → 成员/部门”授权入口兼容，两个入口最终写入同一张表。

本期不改变“部门授权”的语义，也不新增一套成员权限系统；本期的“批量”指一次给一个碳基员工授权多个硅基员工。给多个碳基员工同时授权作为后续扩展，不作为本期交付目标。

## 2. 调研结论

### 2.1 现有数据模型可以直接承载

`backend/prisma/schema.prisma` 中的 `EmployeeGrant` 已经满足本需求：

- `subscriptionId` 指向企业雇佣的硅基员工。
- `memberId` 指向单个碳基员工。
- `departmentId` 指向部门；与 `memberId` 二选一。
- `expiresAt = null` 表示长期授权。
- 数据库已有按 `(subscriptionId, memberId)` 的部分唯一索引，直接授权天然幂等。

因此无需新增 Prisma model 或迁移。新入口只需要写入已有的 `EmployeeGrant(memberId=...)` 记录。

### 2.2 现有服务和接口可复用，但方向相反

当前后端位于：

- `backend/src/modules/enterprise/grant.service.ts`
- `backend/src/modules/enterprise/enterprise.controller.ts`
- `backend/src/shared/employee-grant.dto.ts`

已有接口：

- `GET /enterprise/subscriptions/:id/grants`：查看一个硅基员工授权给谁。
- `POST /enterprise/subscriptions/:id/grants`：单条授权。
- `POST /enterprise/subscriptions/:id/grants/batch`：一个硅基员工批量授权给多个成员或部门。
- `DELETE /enterprise/grants/:id`：收回授权。
- `GET /enterprise/my-employees`：当前成员能使用哪些硅基员工。

现有 `GrantService.createBatch()` 已处理企业隔离、管理员校验、目标校验、过期授权续期、并发锁和重复授权跳过逻辑，但它的批次主键是一个 `subscriptionId`。本需求需要增加“固定一个 `memberId`，批量写入多个 `subscriptionId`”的对称服务方法。

### 2.3 当前前端入口

`web/src/app/(enterprise)/members/page.tsx` 当前只展示成员、角色、部门、职位，并提供编辑和移出操作。
`web/src/features/enterprise/grant-panel.tsx` 是现有硅基员工侧授权面板，已经有成员搜索、分页、多选、重复授权跳过和过期授权续期的交互，可以复用其选择器和状态文案。

### 2.4 权限边界

现有授权写操作只允许 `ENTERPRISE_ADMIN`。本需求沿用该规则：

- 企业管理员：可查看成员授权状态，可新增/续期/收回直接授权。
- 部门负责人、普通成员：看不到授权管理按钮，也不能调用写接口。
- 所有 `memberId`、`subscriptionId` 必须属于当前企业；跨企业 ID 统一返回 404 或 400，不泄漏资源是否存在。

## 3. 产品与交互设计

### 3.1 成员列表入口

在 `/members` 表格中，管理员视角新增一列“硅基员工”或“授权”列，展示：

- `已授权 N 位`：只统计当前成员的直接授权。
- 若成员所在部门有部门授权，可在数字旁显示“部门覆盖 M 位”，避免把部门授权误认为直接授权。
- 无授权显示 `未授权`。

操作列新增钥匙/用户权限图标按钮，标题为“授权硅基员工”。保留现有编辑、移出按钮。普通成员不渲染该按钮。

不建议把完整硅基员工名称堆进表格行：成员页的主要任务是比较成员，授权明细放到侧滑面板/弹窗中更适合扫描。

### 3.2 授权面板

点击某行“授权硅基员工”后打开 `MemberEmployeeGrantPanel`：

**头部**

- 碳基员工姓名、邮箱、部门、职位。
- 当前直接授权数、部门覆盖数。
- 关闭按钮。

**筛选区**

- 关键词搜索：匹配企业内称呼、模板名、岗位。
- 状态筛选：`全部`、`可授权`、`已授权`、`已暂停`。
- 默认只展示 `ACTIVE`/`PAUSED` 雇佣关系；`EXPIRED`/`TERMINATED` 仅在“历史”筛选中展示且不可新增授权。

**列表区**

每行显示：

- 复选框。
- 硅基员工头像、企业内称呼、模板名/岗位。
- 雇佣状态：使用中、已暂停、已结束。
- 授权状态：
  - `未授权`
  - `已直接授权`，附授权到期时间或“长期有效”
  - `部门已覆盖`，说明当前成员因部门授权已经可以使用
  - `已过期`，允许勾选后续期
- 已直接授权行提供“收回”按钮；收回前二次确认。

**底部操作栏**

- 显示“已选择 N 位硅基员工”。
- 到期方式：`长期有效`、`设置到期日期`。
- 当选择包含已过期直接授权时显示“续期已过期授权”开关，默认关闭。
- 主按钮：`授权 N 位`。
- 提交后展示结果摘要：`成功新增 X 位，续期 Y 位，已跳过 Z 位`。

### 3.3 部门覆盖的处理

部门授权和直接授权是两条独立记录，`myEmployees()` 会合并并优先标记直接授权。面板需要明确告诉管理员：

- “部门已覆盖”不等于存在直接授权记录。
- 仍可创建直接授权，用于成员调岗后继续保留权限，或形成独立的个人授权周期。
- 如果管理员只想依赖部门授权，应保持不勾选；不自动生成冗余直接授权。

### 3.4 成功、失败与并发提示

- 全批次成功：`已授权 3 位硅基员工给姚瑞泉`。
- 部分跳过：`新增 2 位，已存在 1 位，未改动已存在授权`。
- 发现部门覆盖：在结果中单列 `其中 1 位原本已由部门覆盖`，但不算失败。
- 雇佣关系在提交期间变为结束/跨企业：该项标记失败，其他合法项仍按接口事务规则处理；推荐本期采用“整批校验、整批失败”，避免管理员误以为批次全部成功。
- 目标成员被移出企业：返回 404，关闭或刷新面板并提示“成员已不在当前企业”。

## 4. 后端设计

### 4.1 DTO

在 `backend/src/shared/employee-grant.dto.ts` 增加：

```ts
const memberGrantSubscriptionIds = z
  .array(z.string().trim().min(1))
  .min(1)
  .max(100)
  .refine((ids) => new Set(ids).size === ids.length, '硅基员工不能重复');

export const MemberGrantBatchCreateDtoSchema = z.object({
  subscriptionIds: memberGrantSubscriptionIds,
  expiresAt: z.string().datetime().optional(),
  renewExpired: z.boolean().default(false),
}).strict();

export type MemberGrantBatchCreateDto = z.infer<
  typeof MemberGrantBatchCreateDtoSchema
>;
```

建议共享返回类型：

```ts
export interface MemberGrantBatchResult {
  memberId: string;
  createdIds: string[];             // 新建的 EmployeeGrant id
  renewedSubscriptionIds: string[];
  skippedSubscriptionIds: string[]; // 已存在且未续期
}
```

### 4.2 查询接口

新增：

```http
GET /enterprise/members/:memberId/employee-grants
```

查询参数：

- `keyword`：按企业内称呼、模板名、岗位搜索。
- `status`：`all | grantable | granted | history`，默认 `grantable`。
- `page`：默认 1。
- `pageSize`：默认 20，最大 100。

响应建议：

```ts
interface MemberEmployeeGrantCandidate {
  subscriptionId: string;
  name: string;
  status: 'ACTIVE' | 'PAUSED' | 'EXPIRED' | 'TERMINATED';
  endDate: string | null;
  employee: {
    id: string;
    name: string;
    avatar: string | null;
    position: string;
  };
  directGrant: {
    id: string;
    expiresAt: string | null;
    expired: boolean;
  } | null;
  coveredByDepartment: boolean;
}

interface MemberEmployeeGrantCandidatesResponse {
  items: MemberEmployeeGrantCandidate[];
  page: number;
  pageSize: number;
  total: number;
}
```

查询必须由服务端根据当前用户的 `enterpriseId` 过滤，不能接受客户端传入企业 ID。`coveredByDepartment` 只依据成员当前 `departmentId` 和该部门有效授权计算，过期的部门授权不算覆盖。

### 4.3 批量授权接口

新增：

```http
POST /enterprise/members/:memberId/employee-grants/batch
```

请求体：

```json
{
  "subscriptionIds": ["sub_1", "sub_2"],
  "expiresAt": "2027-12-31T23:59:59.000Z",
  "renewExpired": false
}
```

规则：

1. 仅 `ENTERPRISE_ADMIN` 可调用。
2. 校验 `memberId` 属于当前企业。
3. 按排序后的 ID 顺序锁定成员、订阅和相关授权记录，避免与现有“硅基员工侧批量授权”、收回授权、成员移出并发时丢数据。
4. 所有 `subscriptionIds` 必须属于当前企业。
5. 只有 `ACTIVE` 或 `PAUSED` 订阅可新增授权；`EXPIRED`、`TERMINATED` 拒绝整批请求。
6. `expiresAt` 为空表示长期有效，非空必须晚于当前时间。
7. 已存在且未过期的直接授权进入 `skippedSubscriptionIds`。
8. 已存在但已过期的直接授权：仅当 `renewExpired=true` 时更新 `expiresAt`，否则跳过。
9. 一次最多 100 个硅基员工；单选场景传一个元素即可，不再额外维护单条接口。
10. 返回 200，结果包含新增、续期、跳过 ID；写操作需要记录 `AuditLog`，`summary` 只保存数量和资源 ID，不保存请求正文。

建议服务方法：

```ts
GrantService.createBatchForMember(
  userId: string,
  memberId: string,
  dto: MemberGrantBatchCreateDto,
): Promise<MemberGrantBatchResult>
```

### 4.4 收回接口

继续复用：

```http
DELETE /enterprise/grants/:grantId
```

删除前必须校验授权记录所属企业。收回直接授权不会删除部门授权；若该成员仍被部门覆盖，收回后仍可使用硅基员工，这是预期行为，前端需在确认文案中说明。

### 4.5 Controller 与模块

在 `EnterpriseController` 增加两个路由，使用 `ZodValidationPipe` 和现有 Swagger 装饰器：

- `GET members/:memberId/employee-grants`
- `POST members/:memberId/employee-grants/batch`

不新增模块；继续由 `enterprise` 模块注入 `GrantService`。不修改 Prisma schema，不执行迁移。

## 6. 数据与并发安全

### 6.1 不新增表、不改变既有授权语义

本需求只新增 `EmployeeGrant(memberId=...)` 记录。部门授权、`myEmployees()` 的直接优先规则、成员移出时回收个人授权的行为均保持不变。

### 6.2 事务策略

批量授权必须在一个 Prisma transaction 中完成：

- 先锁定目标成员，防止与移出企业并发。
- 再锁定订阅行，防止与终止/暂停并发。
- 再读取和锁定现有直接授权。
- 全部目标通过校验后才写入。

本期建议采用“整批校验、整批失败”：一旦存在跨企业、已终止或不存在的订阅，整个请求返回 400/404，不产生部分写入。重复授权属于业务可预期状态，按 `skipped` 返回，不视为失败。

### 6.3 授权有效性

授权是否可用由两层共同决定：

- `Subscription.status === ACTIVE`。
- `EmployeeGrant.expiresAt` 为空或晚于当前时间。

`PAUSED` 订阅可以保留或新建授权，但当前不会出现在成员的“可用硅基员工”列表中；恢复为 `ACTIVE` 后自动生效。这样与现有 `myEmployees()` 逻辑一致。

## 7. 测试计划

### 7.1 后端单测

在 `backend/src/modules/enterprise/grant.service.spec.ts` 增加：

1. 管理员可给本企业成员单个授权。
2. 管理员可一次授权 2 个硅基员工。
3. 重复直接授权进入 `skipped`，不产生第二条记录。
4. `renewExpired=true` 可续期已过期直接授权。

6. 跨企业成员或订阅被拒绝，且事务不落部分数据。
7. 普通成员/部门负责人调用写接口返回 403。
8. `PAUSED` 可保留授权，`EXPIRED`/`TERMINATED` 不可新增。

## 8. 开发顺序与交付拆分

1. **后端契约**：DTO、候选查询、成员维度批量授权 service/controller、Swagger。
2. **后端验证**：单测、E2E、审计日志和并发锁验证。
3. **前端数据层**：类型、query key、hooks。
4. **前端面板**：选择、筛选、分页、授权、续期、收回。
5. **成员页接入**：授权按钮、计数/面板、权限态。
6. **回归验证**：现有硅基员工侧 `GrantPanel`、订阅页、`my-employees` 页面不受影响。

## 9. 验收标准

- 管理员在 `/members` 找到一个碳基员工，打开授权面板即可看到本企业可授权的硅基员工。
- 选择 1 个硅基员工可以完成授权；选择多个可以一次提交并看到新增/跳过/续期结果。
- 重复点击不会产生重复 `EmployeeGrant`。
- 只有当前企业管理员能写授权；跨企业成员、订阅 ID 不可操作。
- 收回直接授权后，若无部门覆盖，该成员立即从“我的硅基员工”中消失。
- 成员移出企业时，新增的直接授权会与现有逻辑一样被回收，部门授权不受影响。
- 现有从 `/subscriptions` 发起的成员/部门授权继续可用。
- 后端对应单测、前端组件测试和授权 E2E 均通过；不需要数据库迁移。

## 10. 后续扩展

以下能力不纳入本期，但接口可保留扩展空间：

- 在成员表中多选多个碳基员工，再批量授予同一批硅基员工。
- 部门授权的“成员覆盖预览”和批量转为直接授权。
- 授权模板：按岗位/部门保存常用硅基员工组合。
- 授权变更审计页面和导出。
