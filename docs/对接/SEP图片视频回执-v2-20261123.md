# SEP 图片、视频处理流程与客户端回执

更新日期：2026-11-24。本文依据当前工作树代码及 Longdao 的 `sep-media-receipt-contract-20261124.md` 说明修改后的行为，代码尚未部署，不代表线上已生效。适用于真实媒体接口；历史同步任务继续兼容，不涉及 mock 生成。

阅读顺序：第 1 节了解整体，第 2 节按流程看 SEP 如何处理，第 3～6 节供客户端开发对接，第 7～9 节供平台维护与联调使用。

## 1. 整体实现

一次图片或视频任务分为四件事：**提交有没有被接受、生成有没有结束、文件有没有保存、费用有没有结清**。这四件事分别记录、分别回传，避免某一个环节出错后把所有状态都变成“未知”。

```text
客户端读取企业可用的模型配置
  -> 如需参考图，先上传图片，取得 referenceId
  -> 用选定配置和规格向 SEP 报价
  -> 带报价 ID 和客户端请求 ID 提交
  -> SEP 保存任务、预留费用，再向 Longdao 提交一次
  -> 客户端查询原回执；视频也由平台定时恢复原任务
  -> SEP 查询 Longdao 原任务，保存已完成的成品并核对费用
  -> 客户端通过 SEP 下载，保存到本地后再报告“文件已保存”
```

所有模型请求均经 Longdao/sub2api。客户端不接触 Longdao Key，不直接调用脑生云。

本次没有新增消息队列或独立 Worker。图片新请求明确使用异步上游；提交接口仍需等待本次“创建任务”的回执，不意味着 SEP 收到请求后立刻在后台排队执行。

| 对比项 | 修改前 | 修改后 |
|---|---|---|
| 图片 | 主要按同步返回处理 | 新请求统一异步，查询原任务取得结果 |
| 任务状态 | 客户端主要依赖顶层 status 推断 | 新增提交、生成、文件、账务的独立字段 |
| 错误信息 | 已有 upstreamError，不同阶段可能混在一起 | 分别保留任务、查询/下载和账务的具体错误 |
| 提交断线 | 可能长期无法确认原任务 | 保存原请求标识，通过 Longdao 恢复原任务 |
| 明确提交失败 | 可能继续处于待核对或未知 | 关闭生成；确认不扣费后释放原冻结 |
| 客户端下一步 | 主要自行判断 | 明确返回继续查什么、能否重试下载、能否新建任务 |

## 2. SEP 按步骤如何处理

### 2.1 下发能力

客户端读取图片或视频的 profiles 接口。SEP 根据企业授权、Profile 启用与校验状态、执行开关、连接和适配器状态计算可执行能力。

客户端只应展示已授权且适配器可执行的操作。Profile 内的尺寸、质量等提示不等于上游已实际生成验证通过；最终请求还会经过规格校验、报价和提交检查。

新图片能力下发为异步，支持任务查询、不支持取消。每次输出 1 张，参考图实际最大数量取后台配置与 4 张协议上限中的较小值。视频的参考图数量和取消能力按配置及适配器能力判断。

### 2.2 上传参考图

客户端每次向 SEP 上传一个名为 file 的 multipart 文件。多张图片分别上传，收集多个 referenceId；正式生成时传有序的 referenceIds 数组。

SEP 校验文件真实格式、大小和图片内容，保存原始字节，不统一转 PNG。元数据记录 referenceId、MIME、尺寸、字节数、SHA256 和过期时间，并绑定企业、成员、用户、订阅作用域。

图片参考文件单张最多 5 MiB；视频参考文件单张最多 10 MiB，配置更低时按配置限制。支持 JPG/JPEG、PNG、WebP，暂不支持 HEIC。参考图有效期为 15 分钟。

使用时 SEP 再检查归属、过期时间、数量和文件完整性。referenceIds 的顺序就是提交给 Longdao 的顺序，不能引用其他用户的 ID。

### 2.3 报价

客户端传 Profile、配置版本、提示词、参考图 ID 和规格。SEP 执行以下检查：

1. 认证、成员和订阅是否有效，企业是否授权该配置。
2. 配置版本、操作、参考图和请求规格是否可执行，必要计价字段是否齐全。
3. 请求内容和参考图摘要是否一致，是否存在尺寸、比例等冲突。
4. 向 Longdao 询价，并核对模型、规格、金额、价格版本和有效期。
5. 按当前汇率换算人民币，计算资金来源，保存报价快照。

报价只询价，**不创建生成任务，也不冻结钱包**。图片和视频的报价有效期均最多 60 秒，并受 Longdao 报价有效期限制，以 expiresAt 为准。

### 2.4 创建任务并预留费用

客户端在第一次提交前生成 clientRequestId，并保存本次参数与 quoteId。SEP 先查该 ID 是否已使用：

- 同一 ID、同一原报价和参数：返回或恢复原回执，不再次生成。
- 同一 ID 换了参数、参考图或报价：返回冲突，不能当成新任务使用。
- 没有原记录：检查报价及连接快照，再创建 SEP 任务记录。

SEP 在调用 Longdao 之前就生成并保存 execution.requestId，因此即使没有收到 Longdao 任务编号，也有恢复依据。

随后 SEP 按报价预留资金。资金分配沿用现有订阅算力、成员可用资金和个人钱包规则。预留是为了防止余额在多个任务之间重复使用，不是确认最终消费。

| 情况 | SEP 行为 |
|---|---|
| 明确余额不足 | 不提交 Longdao，保存失败回执，billingStatus=NOT_RESERVED |
| 预留操作结果不确定 | 不提交 Longdao，保存具体 billingError，等待核对 |
| 预留成功 | 再检查授权、配置和连接，保存“即将派发”的状态，随后提交一次 |
| 派发前配置或权限改变 | 不提交 Longdao，结束本次请求并尝试释放预留资金 |

### 2.5 向 Longdao 提交

SEP 用保存的 requestId 同时填写 X-Client-Request-ID 和 Idempotency-Key。客户端不需要自己拼这些 Longdao 请求头。

| 操作 | SEP 调用 Longdao |
|---|---|
| 文生图 | POST /v1/images/generations/async，JSON，n=1、response_format=url |
| 图生图 | POST /v1/images/edits/async，multipart，重复的 image[] 文件字段 |
| 文生视频 | POST /v1/videos，JSON |
| 图生视频 | POST /v1/videos，multipart，重复的 input_reference 文件字段 |

SEP 根据 Profile 找到上游 model，并把客户端规格映射成上游字段。例如图片 count 对应 n，视频 durationSeconds 对应 seconds。参考图按原格式上传。

视频目前不向 Longdao 发送 fps；客户端若提交 frameRate，成品仍报告实际测得帧率，不单独因上游选择其他帧率就判定 V3 成品不匹配。

SEP 不追加生成重试。Longdao 图片上游只提交一次；适用本次视频协议的 Longdao 内部最多四次，间隔 1、2、4 秒。其重试结果随 submissionRetry 返回。

### 2.6 接收提交结果

SEP 即使收到 Longdao 非 2xx，也会检查正文有没有可靠的任务、提交和账务信息，不能只看 HTTP 状态。

| Longdao 结果 | SEP 处理 | 客户端得到的含义 |
|---|---|---|
| accepted，拿到任务编号 | 保存编号，后续查原任务 | 已受理，继续等待生成 |
| submitting | 保留提交状态 | 仍在创建，继续查询 |
| failed/rejected/not_submitted，且 not_charged | 关闭生成，尝试释放预留资金 | 本次结束，可由用户重新发起 |
| protocol_error，保留任务编号 | 按 Longdao 明确关闭的提交处理；确认不扣费后释放预留 | 显示协议错误，结束生成；任务编号仅用于诊断，不重复创建 |
| 明确提交失败，但账务 unknown | 生成结束，费用待核对 | 可新建任务，不宣称免费 |
| SEP 预留费用异常，确认尚未派发 | 生成失败、submissionStatus=not_submitted；钱包继续核对 | 不显示提交不明，也不提前声称预留已退款 |
| SEP 与 Longdao 断线或回执无法验证 | 保留具体错误，按原标识恢复 | 暂未确认提交结果，不自动重提 |
| 回执中有可靠任务编号但其他字段异常 | 尽量保存可靠编号和错误，继续恢复 | 不丢掉已取得的原任务关联 |

taskId 为 null 本身不能证明失败或未扣费。必须结合明确的提交结果和账务证据。

### 2.7 查询与断线恢复

客户端拿到 receiptId 后查询原回执；没有收到 receiptId 时，用已保存的 clientRequestId 查询 SEP。

SEP 有 Longdao taskId 时按任务编号查；没有时按原 requestId 查：

| 类型 | 按任务查 | 按原请求标识恢复 |
|---|---|---|
| 图片 | GET /v1/images/tasks/{taskId} | GET /v1/images/tasks/{requestId}?id_type=request_id |
| 视频 | GET /v1/videos/{taskId} | GET /v1/videos/{requestId}?id_type=request_id |

必须使用创建时同一个 Longdao Key。SEP 保存连接指纹，连接地址或 Key 改变后，不会擅自换新 Key 查询原任务；回执保留具体配置变更原因。

查询发生超时、404、503 等错误时，保留此前已经确认的生成状态，并记录 operationError。404 不能证明没接单或没扣费。

Longdao 新回执中的 unobserved 表示本次查询、取消或下载没有取得有权限的原任务证据。即使其中 request_id 是本次查询的新编号，SEP 也只保存这次操作错误，不用它覆盖原 requestId、taskId、提交状态、生成状态或已确认账务。客户端可在 execution.operationError.body 中看到这份原始回执。not_applicable 仅用于报价等非生成操作，不作为生成任务结果。

Longdao 报价的新 schema_version=2 和旧 schema_version=1 均可识别，业务 operation 仍为 generate/edit/text-to-video/image-to-video，receipt_operation=pricing 只描述本次接口用途。用量响应顶层 status 是账务状态，不能当成生成状态。

对 SEP 确认从未派发的记录，超过本地提交保护期限后可以关闭并尝试退款；已经开始向 Longdao 派发的记录，必须查原请求，不能仅凭 SEP 超时就假报免费。

新异步任务由客户端查询驱动恢复、交付和核账，本次没有新增后台定时轮询。没有后续查询时，不保证 SEP 自动取得最新终态或自动完成核账。

### 2.8 保存成品与客户端下载

Longdao 确认生成 completed 后，SEP 通过它的 content 接口取得原文件，校验并保存：

- 图片校验 MIME、文件内容、尺寸和字节限制，保留 PNG/JPEG/WebP 原始格式。
- 视频校验文件及测量时长、宽高、实际帧率、音频信息；V3 同时返回 deliveryStatus 表示与请求规格的匹配情况。
- 安全且可交付的 V3 原文件即使规格不完全符合，也可保留供下载，并明确标记不匹配；不因此自动重生或直接退款。
- 下载或保存失败时，保留生成 completed，把 fileStatus 设为 download_failed，回传具体错误。

客户端随后继续查询同一回执，可重试 SEP 获取成品，不再创建生成任务。已经结算的原任务，不因重试下载而重复结算。超过保存期限后返回过期，不自动重新生成。

视频获取成品重试成功后会清除已经解决的下载 operationError，不把旧下载失败继续当作当前错误。历史 submissionError、submissionRecordError 和未解决的账务诊断分别保留。

**fileStatus=available 只表示 SEP 已保存可下载文件，不表示客户端已保存到用户电脑。**客户端必须下载成功、校验完整性并写入本地成功后，才告知用户“文件已保存”。

客户端下载途中断流时可能收不到 JSON 错误；必须检查网络结果、文件长度及 SHA256，不能把部分文件当作成功成品。

### 2.9 结算或释放资金

Longdao 和 SEP 的账务分别表达，不能只看其中一个字段。

| 证据 | SEP 处理 |
|---|---|
| Longdao 明确 not_charged | 释放原预留；成功后 RELEASED，失败则 RECONCILING 并返回 billingError |
| Longdao settled | 再按原 requestId 查询账务证据，核对模型、金额及相关计价规格，用冻结汇率结算 |
| Longdao pending/unknown | 不推断成零费用，不凭猜测释放或扣费，继续待核对 |
| SEP 账务已结算或已释放 | 复用已确认结果，不执行第二次结算或退款 |
| 实际费用超过 SEP 原预留 | 进入 RECONCILING，当前实现不会据此擅自无限追加扣款 |

图片账务查询使用 GET /v1/sub2api/usage?request_id=...，兼容 v1 和 v2；新异步 v2 可能不返回 image_count，SEP 按每次 1 张的协议、原请求、模型和金额核验。视频使用 GET /v1/sub2api/videos/usage?request_id=...，还核对视频数量、时长和分辨率。

生成是否结束和费用是否核对完成相互独立。账务异常不能让已完成的生成重新变成“生成中”，也不应阻止已有文件下载。

## 3. 客户端接口与请求

### 3.1 接口清单

下面给出完整 /api 前缀。表中的“图片基路径”是 /api/gateway/v1/media/real；“视频基路径”是 /api/gateway/v1/media/video-real。

| 操作 | 方法与相对基路径 | 返回 |
|---|---|---|
| 可用能力 | GET /profiles?protocolVersion=3 | 200，配置和适配器能力 |
| 上传单张参考图 | POST /references | 201，参考图描述与 referenceId |
| 报价 | POST /quotes | 201，quoteId、金额、有效期及规格 |
| 创建或重放原请求 | POST /requests | 202 或 200，任务回执 |
| 用客户端 ID 恢复 | GET /requests/by-client-id/{clientRequestId} | 200，原任务回执 |
| 查询原回执 | GET /requests/{receiptId} | 200，原任务回执 |
| 下载成品 | GET /requests/{receiptId}/outputs/{outputId}/content | 200，二进制文件 |
| 取消 | POST /requests/{receiptId}/cancel | 视频仅在 recovery.canCancel=true 时提供入口；图片不支持 |

JSON 接口请求头：

```http
Authorization: Bearer <employment token>
Content-Type: application/json
```

GET 不需要请求体。上传使用 multipart/form-data，唯一文件字段 file，不额外发送 JSON 字段，让 HTTP 库生成 multipart boundary。取消使用空对象 {}，收到回执后判断实际结果，不能因为请求成功就认定取消成功或退款。

clientRequestId、quoteId、referenceId、receiptId、outputId 使用 1～128 个英文字母、数字、下划线或连字符；不要混用不同类型的 ID。Profile 和配置版本遵循能力接口的 V3 格式，原样使用返回值。

### 3.2 图片 V3 请求

报价 POST /api/gateway/v1/media/real/quotes：

```json
{
  "protocolVersion": 3,
  "profileId": "gpt-image-2-1k",
  "configVersion": "cfg_example",
  "operation": "generate",
  "referenceIds": [],
  "creativeBrief": "清晨草地上的一只小猫，写实摄影风格。",
  "requestedSpec": {
    "size": "1024x1024",
    "count": 1,
    "quality": "medium"
  },
  "parameterSources": {
    "size": "user",
    "count": "user",
    "quality": "model"
  },
  "specRevision": 1
}
```

创建 POST /api/gateway/v1/media/real/requests：使用完全相同的报价请求体，再加上 quoteId 和 clientRequestId。

```json
{
  "protocolVersion": 3,
  "profileId": "gpt-image-2-1k",
  "configVersion": "cfg_example",
  "operation": "generate",
  "referenceIds": [],
  "creativeBrief": "清晨草地上的一只小猫，写实摄影风格。",
  "requestedSpec": {
    "size": "1024x1024",
    "count": 1,
    "quality": "medium"
  },
  "parameterSources": {
    "size": "user",
    "count": "user",
    "quality": "model"
  },
  "specRevision": 1,
  "quoteId": "quote_example_1",
  "clientRequestId": "client_image_example_1"
}
```

图生图改成 operation=edit，referenceIds 填入 1～4 个已上传且仍有效的 ID，并受当前配置的更低数量限制。文生图 generate 不带参考图。

size、count、quality 是当前图片适配器的必要计价字段。parameterSources 记录参数由用户、模型或上游提出，不是模型名称，不改变实际规格，也不会绕过校验。规格变化后重新报价，并使用新的请求标识创建新任务。

### 3.3 视频 V3 请求

报价 POST /api/gateway/v1/media/video-real/quotes：

```json
{
  "protocolVersion": 3,
  "profileId": "seedance-prod",
  "configVersion": "cfg_example",
  "operation": "image-to-video",
  "referenceIds": ["reference_front", "reference_side"],
  "creativeBrief": "根据两张商品图片生成展示视频，镜头缓慢推进。",
  "requestedSpec": {
    "durationSeconds": 4,
    "resolution": "720p",
    "aspectRatio": "16:9",
    "audio": true,
    "outputFormat": "video/mp4"
  },
  "specRevision": 1
}
```

创建时同样追加 quoteId 和 clientRequestId。文生视频使用 text-to-video、referenceIds=[]。durationSeconds、resolution 是当前视频必要计价字段；其他规格按能力和适配器支持填写。

示例 Profile、版本、ID、质量和音频选项均为示意，必须替换成能力接口和真实上传、报价返回的值，不保证任意账号均支持此组合。

### 3.4 HTTP 状态怎么读

| 返回情况 | 客户端处理 |
|---|---|
| 创建 202 | SEP 已有回执，顶层状态为 SUBMITTING、SUBMISSION_UNKNOWN、QUEUED 或 RUNNING；按正文判断继续查什么 |
| 创建 200 | 读取原回执，可能是成功，也可能是明确失败、取消或过期 |
| 查询 200 | 只是成功返回回执，不代表生成成功 |
| 非 2xx JSON | 保留状态和原错误正文；可能是认证、参数、报价、存储或上游错误，不保证已有 receiptId |
| 下载 200 | 按文件读取，不能当 JSON；仍要确认文件完整保存 |

余额不足可能在报价阶段返回非 2xx；若在创建并保存任务后才发现不足，则可以返回 status=FAILED、billingStatus=NOT_RESERVED、billingError.status=402 的完整回执。客户端两种返回都要处理。

## 4. 回执字段

### 4.1 版本与标识

请求 protocolVersion=3、回执 receiptVersion=2 保持不变。本次是在尚未发布的回执上补充状态和错误字段，客户端需按本文更新严格字段及枚举校验；二者与 Longdao 的 schema_version 是三套用途不同的版本号。

| 字段 | 含义与客户端用途 |
|---|---|
| mock | 真实执行为 false |
| clientRequestId | 客户端创建的本次请求 ID，提交前本地持久保存；未拿到回执时用它恢复 |
| receiptId | SEP 回执 ID，查询和下载使用 |
| profileId / configVersion | 本次选择的配置及版本 |
| execution.requestId | SEP 提交 Longdao 时保存的原标识，用于后台恢复与排查 |
| execution.taskId | Longdao 任务编号；尚未取得时 null |
| protocolVersion / specRevision / semanticHashVersion | V3 请求协议、规格修订及内容摘要版本；保持与本次请求关联 |
| executionMode | 图片新回执为 async-query，历史图片可能为 sync-response；不要要求视频回执一定有这个顶层字段 |

### 4.2 提交、生成、文件与账务

| 字段 | 可选值或含义 |
|---|---|
| status | 历史综合状态：SUBMITTING、SUBMISSION_UNKNOWN、QUEUED、RUNNING、SUCCEEDED、PARTIAL_SUCCEEDED、FAILED、CANCELLED、RESULT_EXPIRED |
| execution.submissionStatus | not_submitted、submitting、rejected、accepted、failed、protocol_error、unknown；共享类型还识别 unobserved/not_applicable，但不会用查询无证据或报价响应覆盖原任务 |
| execution.generationStatus | queued、in_progress、completed、failed、cancelled；没有可靠状态时 null |
| execution.isFinal | 生成状态是否已确认终态，可能为 null；提交明确失败时仍应结合 generationFinished 判断本次流程已结束 |
| execution.statusSource | upstream 或 cached，缺失时 null |
| execution.observedAt | 状态确认时间，毫秒时间戳，缺失时 null |
| fileStatus | pending、available、download_failed、expired、unavailable |
| execution.billing.status | Longdao 账务：pending、settled、not_charged、unknown |
| execution.billing.actualCostUsd | Longdao 确认的美元金额字符串；未知时 null，不得显示成 0 |
| billingStatus | SEP 钱包：NOT_RESERVED、RESERVED、SETTLED、RELEASED、RECONCILING |
| outputs | SEP 已保存的成品描述数组，包括 outputId、MIME、字节数、SHA256、尺寸、expiresAt；视频还有时长与实际帧率 |
| effectiveSpec / actualSpec | 本次采用的规格 / 从成品确认的实际规格；actualSpec 不一定已经取得 |
| acceptance | 图片 V3 的匹配结果、已确认不匹配字段和仍未知字段 |
| deliveryStatus | 视频 V3 的 matched、mismatched 或 unknown，不等于账务状态 |
| amountCny / amountUsd | 视频回执内保留的报价金额，不是最终实扣金额 |
| actualCostCny | 视频确认结算后可返回的人民币实际金额；图片回执当前没有统一的人民币实扣字段，不自行添加或推算成已确认金额 |
| outputErrors | 图片历史输出错误列表；本次新图片 n=1 |

顶层 status 不是四个维度的替代品。例如生成已 completed，但下载失败时顶层仍可能为 RUNNING；客户端必须按 execution 和 clientActions 判断生成已经结束。

### 4.3 错误详情

| 字段 | 表示哪类错误 |
|---|---|
| errorCode | SEP 的摘要错误码，供程序分类，不能代替具体错误消息 |
| upstreamError | 保留已有的兼容错误入口 |
| execution.taskError | 任务本身失败，例如上游拒绝参考图 |
| execution.operationError | 提交、查询、取消或下载操作异常 |
| execution.operation | 最近一次收到的 Longdao 操作用途：create/query/cancel/download；不是图片 generate/edit 或视频 text-to-video/image-to-video |
| execution.submissionError | 原创建失败原因，保留原 code、message、details 等；恢复查询成功后仍保留 |
| execution.submissionHttpStatus | 原创建响应的 HTTP 状态，例如 422 或 502；不是当前 SEP 查询接口的 HTTP 状态 |
| execution.submissionRecordError | Longdao 保存失败回执时发生的异常；与原生成错误分开 |
| execution.diagnosticTruncated | true 表示 Longdao 明确说明诊断被截断，不能宣称错误详情完整 |
| execution.billing.error | Longdao 自身的账务异常 |
| billingError | SEP 自身的预留、退款或结算异常 |
| execution.submissionRetry | Longdao 视频重试详情，包括其原始 attempts、exhausted 和各次错误等字段 |

operationError、billingError、upstreamError 的结构为 status、body、可选 headers。body 可以是对象、数组、字符串等 JSON 值，不要求一定有 code 或固定层级的 message。

submissionError、submissionRecordError、taskError 和 execution.billing.error 则直接保存脱敏后的 JSON 诊断，不额外包裹 status/body。成功恢复查询可没有 operationError，但 submissionError 仍可存在；客户端不能将原创建错误误报成“本次查询失败”。

展示时按当前出错阶段找具体 message；没有 message 时把原正文作为文本或格式化 JSON 展示。任务错误、操作错误和费用错误可以并列显示，不用后发生的费用异常覆盖原生成错误。

错误信息保留上游具体原因，但会遮蔽 Key 等敏感信息，并受到诊断内容读取上限约束；不是逐字无限制透传。错误详情里的 status 是该错误来源的 HTTP 状态，不一定等于本次 SEP 响应的 HTTP 状态。

### 4.4 客户端下一步

| clientActions 字段 | 含义 |
|---|---|
| submissionFinished | 本次提交结果是否已经结束确认 |
| generationFinished | 本次生成流程是否结束，包含未成功创建任务的明确失败 |
| shouldPoll | 是否还需要查询原回执 |
| pollPurpose | submission：恢复提交；generation：等待生成；delivery：重试取得成品；billing：单独核账；none：无需继续 |
| canStartNewRequest | 允许用户主动发起另一项生成；仍需重新报价、检查余额，不是自动重提，也不是免费额度 |
| canRetryDownload | 原任务已生成完成，但 SEP 保存失败，可以查询原回执以重试取得成品 |

recovery.canQuery、canDownload、canCancel 继续保留。新回执以 clientActions 说明查询目的，以 recovery.canDownload 判断 SEP 成品下载入口是否可用。

pollAfterMs 是建议下次查询间隔：通常为 3000，单独核账时为 15000，无需查询时 null。客户端应避免同一任务重叠查询，并在请求本身失败时退避。

## 6. 客户端处理规则

1. 提交前持久保存 clientRequestId、quoteId 和完整原请求；收到回执后保存 receiptId 与原始回执 JSON。
2. 同时接受创建接口的 200 和 202，读取正文，不根据 HTTP 成功直接报告生成成功。
3. 生成是否结束优先看 generationFinished；文件是否可取看 fileStatus、outputs 和 canDownload；费用单独展示。
4. shouldPoll=true 时按 pollAfterMs 查询原回执；pollPurpose=billing 时结束生成中的界面状态，仅继续核账。
5. 提交连接断开先用 clientRequestId 恢复，不自动换 ID 创建，不把查询 404 当作免费失败。
6. canStartNewRequest=true 只解锁用户主动发起新的生成。新任务重新报价、重新生成 ID；重试下载不使用新 ID。
7. 下载按 MIME 选择扩展名，核对字节数和 SHA256，成功写入用户目录后再回报本地保存成功。
8. 重试查询本身失败时保留最后已知状态和错误详情；不擅自覆盖生成终态。
9. 更新严格 JSON 解析，接受新回执字段、图片异步模式、NOT_RESERVED 和 JPEG/WebP 输出；没有新字段的历史回执仍按历史协议读取。
10. protocol_error 是明确结束的提交错误，不能再归类为“提交不明”。保留 taskId 不代表可重复提交或必须继续等生成；以 clientActions 为准。
11. 原创建失败原因使用 submissionError，本次操作错误使用 operationError，Longdao 保存回执失败使用 submissionRecordError，三个原因可同时展示。查询无证据时保留原任务状态，不能推断失败、不扣费或重新提交。

## 7. 期限、存储与并发

### 7.1 超时配置

| 项目 | 图片 | 视频 |
|---|---|---|
| Longdao 上游创建预算 | 60 秒 | 247 秒 |
| 提交中断保存宽限 | 10 秒 | 10 秒 |
| SEP 本地未派发记录的提交保护期限 | 创建 SEP 记录后 70 秒 | 创建 SEP 记录后 257 秒 |
| SEP 向 Longdao 的创建 HTTP 等待上限 | 90 秒 | 300 秒 |
| Next API 代理默认等待上限 | 330 秒 | 330 秒 |
| Longdao 原任务/请求索引保留 | 24 小时 | 7 天 |

Longdao 本次新增的“没有任务编号的明确失败回执”单独缓存 7 天；已经登记本地任务编号的图片仍受原图片任务索引 24 小时限制。SEP 不把失败缓存的 7 天理解成图片任务或成品都可访问 7 天，实际以 Longdao 记录及其过期信息为准。

本地提交保护期限与 Longdao 创建预算对齐，但各自从自己的记录创建时开始计时，不是双方共享同一绝对截止时间。这些都是提交阶段预算，不是生成视频的最长运行时间。

客户端等待需覆盖 SEP 前置校验和 Longdao 创建，建议留足余量；视频创建建议至少 330 秒。外部 Nginx、负载均衡，以及既有 SEP_API_PROXY_TIMEOUT_MS 显式设置也要核对，默认值修改不会覆盖已有配置。

### 7.2 数据存在哪里

| 内容 | SEP 存储 |
|---|---|
| 模型配置和授权 | PostgreSQL 的 media_model_profiles 及企业模型配置 |
| 图片参考元数据、报价、任务与回执 | media_real_references、media_real_quotes、media_real_requests |
| 视频参考元数据、报价、任务与回执 | media_gateway_references、media_gateway_quotes、media_gateway_requests |
| 图片和视频资金预留与结算依据 | media_real_billing_reservations，完成结算后关联现有使用记录 |
| 图片参考图与成品原始字节 | Redis，参考图 15 分钟、成品窗口 24 小时 |
| 视频参考图与成品 | 文件缓存；MEDIA_VIDEO_CACHE_DIR，未设置时使用 UPLOAD_PATH/media-video，UPLOAD_PATH 默认 uploads |

本次不改数据库表结构、不新增迁移，用现有 JSON 字段保存新回执和派发信息。文件过期不等于删除 PostgreSQL 的任务或财务记录。

SEP 首次尝试保存已完成成品时固定其 24 小时窗口，失败重试不延长此窗口。实际可下载性还受到 Longdao 索引、上游文件地址和缓存可用性限制；24 小时不是上游文件地址始终有效的承诺，客户端应尽快下载。

视频后台每 6 小时扫描一页待处理任务，按服务器本地时间每天 00:00、06:00、12:00、18:00 执行，每页最多 20 条、同时处理最多 2 条；处理时间较长时跳过重叠轮次，积压时按 ID 翻页，频率不等于每个任务都能在 6 小时内更新。扫描覆盖文生视频、图生视频和视频生视频，不判断客户端是否在线，也不依赖登录令牌，在关闭新生成开关后继续恢复既有任务。客户端主动查询仍可触发恢复，不受后台扫描间隔限制。它只查询原任务、获取已生成文件和核对原费用，不重新上传素材或提交生成。原提交仍在期限内且没有操作异常时暂不查询，避免干扰正在提交的请求。

后台恢复保留查询、下载和账务异常的具体原因，失败留待下一轮。取得成品前仍检查成员、订阅和 Profile 授权；权限撤销时不会继续保存文件，原费用仍可核对。客户端下次查询使用相同回执，平台保存不代表客户端已经下载到本地。图片本轮没有增加后台生成查询。

视频文件缓存每 12 小时清理一次（服务器本地时间 00:00 和 12:00），每轮最多扫描 1000 个目录项、删除 100 个过期条目；下轮从目录扫描位置继续，避免大量未过期文件挡住后面的过期文件。仅删除有合法过期元数据的私有文件条目，保留任务和账务记录；无效清理证据记录日志并保留，不删除参考视频上传临时目录或其他业务文件。文件过期后立即拒绝下载，物理删除受分批进度影响，积压时可能超过 12 小时才删除。

### 7.3 并发时如何避免重复

创建使用数据库唯一约束识别同一 clientRequestId；派发前保存标记。任务更新使用 revision 版本校验，只允许基于当前版本写入，避免旧请求覆盖新结果。

同一个 SEP 进程内，对同一任务的恢复查询会合并执行。视频后台与客户端恢复另外共用 Redis 每任务租约，不同进程同一时刻由一个实例恢复；租约定时续期，释放只删除自身 token，Redis 不可用时不启动恢复。图片仍只在进程内合并。数据库版本检查和账务事务继续保护状态与资金；租约不代替数据库幂等约束。

账务在短事务内锁定相关用户/企业并更新资金，外部生成等待不占着账务数据库锁。结算和退款检查原记录状态，不能对已结算或已释放记录重复操作。

多实例部署还要保证它们能访问同一图片 Redis 和对应的视频文件存储；本次没有引入共享文件系统或新的队列，也不等于已经完成扩容架构改造。

## 8. 发布与联调

先确认 Longdao 发布了本次视频及异步图片协议，并完成账号、模型权限和报价配置。再协调 SEP 与客户端发布；旧客户端若只接受同步图片或拒绝新增回执字段，不能直接按旧逻辑使用新版返回。

当前本地验证使用模拟上游和测试数据，不代表收费模型、真实账号权限或生产配置已验收。至少联调以下场景：

| 场景 | 验收结果 |
|---|---|
| 图片、视频正常生成 | 有原任务关联，SEP 文件可下载，客户端本地成功保存，费用只结算一次 |
| 明确提交失败 | 失败原因完整，生成结束，不长期显示 unknown；确认不扣费后释放原预留 |
| protocol_error 与 unobserved | 前者结束生成并保留诊断任务号，后者不覆盖原任务；不能混成提交不明或直接退款 |
| 新报价及用量元信息 | 兼容版本 1/2，新增回执字段不导致 PRICE_UNAVAILABLE 或 BILLING_PENDING |
| 按原请求 ID 恢复前置拒绝 | 当前查询成功，原 submissionError 和 submissionHttpStatus 仍完整下发 |
| 视频重试耗尽 | 返回 Longdao 原重试次数和各次错误，SEP 不再追加生成重试 |
| SEP 提交连接断开 | 用原 clientRequestId 恢复同一任务，没有第二次生成 |
| 下载失败后恢复 | 生成 completed 不改变，只重试取得文件，不重复结算 |
| 生成完成但账务异常 | 仍可下载，费用待核对，客户端可主动创建新任务 |
| 查询记录过期或 Key 改变 | 返回具体原因，不虚构免费、不自动重生 |
| 同一 ID 并发提交、并发查询 | 不重复派发，不重复结算/退款，旧状态不覆盖终态 |
| 成品与规格不一致 | V3 返回实际规格及匹配结果，客户端不把可下载原文件丢掉 |
