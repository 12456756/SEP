# 客户端多媒体运行配置接入说明

日期：2026-11-16。

SEP 已实现接口、共享 schema、企业后台预览及平台侧测试。桌面客户端不在本仓库，其设置页面、工具消费、缓存与错误展示仍需按本文接入。当前没有提交、推送或部署。

## 请求

```http
GET /api/client/subscriptions/{subscriptionId}/runtime
Authorization: Bearer <accessToken>
```

`subscriptionId` 从现有订阅列表获得；使用当前登录用户的 access token。平台保留企业、订阅有效期、成员或部门授权检查，没有新增订阅 ID 格式校验。

省略媒体版本时，图片、视频均默认返回完善后的 V3。显式传参等价：

```http
GET /api/client/subscriptions/{subscriptionId}/runtime?mediaProtocolVersion=3&videoProtocolVersion=3
```

这两个查询参数只接受单个字符串 `3`；其他版本、空值、重复参数、数组及未知查询字段返回 400，并保留字段明细。技能产物的 `skillArtifactProtocolVersion` 继续独立协商。

响应带 `Cache-Control: no-store`。查询只读取配置，不进行模型发现、报价、生成、余额预占或扣费。后台修改配置后，只有客户端下次主动请求才能获得新信息。

## 成功响应

完整 JSON 样例：[client-media-runtime-v3.json](../../backend/test/fixtures/client-media-runtime-v3.json)。该样例由共享契约测试直接解析，包含图片空状态和视频配置。

保留员工提示词、聊天模型、技能等原有字段；新增顶层 `fetchedAt`，代表本次响应组装完成时间。`runtime.media` 和 `runtime.video` 始终存在，不返回旧版本格式。

| 字段 | 客户端含义 |
| --- | --- |
| `status` | `empty` 无授权配置；`disabled` 执行开关关闭；`ready` 至少一项可执行；`unavailable` 有配置但均暂不可执行 |
| `executionAvailable` | 至少存在一项当前可执行的已授权配置，不代表有余额或上游一定在线 |
| `defaultProfileId` | 企业指定且当前可执行的默认配置；否则为 `null`，不自动选择第一项 |
| `profiles[].profileId` | 平台配置编号，客户端保存选择和发起生成时使用它 |
| `profiles[].modelId` | 真实模型标识；同一模型可对应多套配置，不能按模型 ID 去重 |
| `profiles[].modelDisplayName` | 没有独立模型名称时使用 `modelId` |
| `profiles[].displayName` | 平台为这套配置填写的名称 |
| `profiles[].configVersion` | 配置版本，用于原有报价和生成流程；不是响应获取时间 |
| `profiles[].unavailableReason` / `unavailableMessage` | 不可用原因和中文说明；可用时都为 `null` |
| `profiles[].parameters` | 按原 `requestedSpec` 参数名组织的结构化说明，替代原 `capabilityHints` |
| `profiles[].constraints` | 有限的 JSON 参数组合规则，无 JavaScript 表达式 |
| `profiles[].referenceRules` | 每种操作的参考图数量、格式和单张大小要求 |

已授权但停用、未验证、执行关闭或连接未就绪的配置仍返回名称和原因。授权指向已删除配置时，不伪造 profile，并在服务端日志中记录引用。数据库或必要配置读取失败按来源错误返回，不能显示为“没有模型”。

## 参数与参考图

共享定义在 `backend/src/shared/media-runtime-parameters.ts`，由 `shared` 导出；运行配置 schema 在 `media-spec.dto.ts`。

| 定义 | 处理方式 |
| --- | --- |
| `type` / `required` / `operations` | 按类型、必填和当前操作渲染及校验 |
| `valuesMode: suggested` | 提供建议选项，允许满足已知硬限制的其他输入，不能变成封闭下拉框 |
| `valuesMode: allowed` | 仅允许列出的选项，有明确适配器依据 |
| `valuesMode: unknown` | 选项未知，不编造默认值或最大值 |
| `minimum` / `maximum` / `step` | 只在实际返回时作为已知数字限制 |
| `default` | 缺省表示未确认默认值；明确的 `false` 必须保留 |
| `support: unsupported` | 不可编辑，也不加入生成请求 |
| `support: unknown` | 信息未确认，不代表能够透传任意新字段 |
| `source` / `confidence` / `observedAt` | 说明证据来源；`verified` 不保证所有组合和所有时间都能执行 |

当前图片参数覆盖 `size/width/height/aspectRatio/count/quality`；视频覆盖 `durationSeconds/resolution/width/height/aspectRatio/audio/outputFormat/frameRate`。未知范围由客户端明确展示为“范围暂未确认”。

目前已确认的适配器边界：

- 图片生成数量上限取后台 Profile 的“最大输出数量”，不超过当前适配器上限 4 张；编辑参考图数量取后台“最大参考图数量”，不超过 4 张，每张 PNG 不超过 5 MiB；纯生成不接受参考图。
- 文生视频不接受参考图；图生视频需要 1 张 PNG，每张大小上限取 profile 配置与 10 MiB 中较小者。
- 视频下载与文件检查仅实现 `video/mp4`；`frameRate` 当前不支持选择。
- 图片报价需要尺寸或完整宽高，以及数量、质量；视频需要时长，以及分辨率或完整宽高。没有确认的规格默认值不由平台补齐。

`requiredTogether` 表示字段成组填写；`requireAny` 表示满足其中一组；`whenAllowed` 表示条件满足时另一个已填写字段仅允许特定选项。共享的 `validateMediaParameterConstraints(spec, operation, constraints)` 返回不满足的 `code/message`，并将明确的 `false` 视为已填写。

`adapter.referenceSupport` 是总体上限，`referenceRules` 是当前操作的精确要求，两者由同一份规则计算。`maxInputBytes` 均为单张大小。后台上传和生成校验继续执行；客户端校验通过不代表最终生成一定成功。

## 图片后台配置

平台管理员进入“系统设置 → 模型管理 → 图片”，在模型下点击“编辑能力配置”。人工创建和自动发现的图片 Profile 均可配置以下内容。

| 后台配置项 | 保存字段 | 客户端 runtime 字段 |
| --- | --- | --- |
| 支持尺寸 | `capabilities.sizes` | `parameters.size.values`，`valuesMode: suggested` |
| 质量选项 | `capabilities.qualities` | `parameters.quality.values`，`valuesMode: suggested` |
| 最大输出数量 | `capabilities.maxOutputs` | `parameters.count.maximum` |
| 最大参考图数量 | `capabilities.maxReferenceCount` | `adapter.referenceSupport.maxCount` 和编辑操作的 `referenceRules[].maxCount` |

尺寸、质量可用逗号或换行输入多项，属于建议值，不能由客户端变成封闭白名单。质量留空或清空后返回 `valuesMode: unknown`，不返回 `values`，不猜测默认质量。输出与参考图数量必须是 1 至 4 的整数；参考图数量仅在支持参考图编辑时生效。仅文生图的配置不接受参考图。

例如“最大输出数量”为 2、“最大参考图数量”为 3、质量为 `auto, medium, high` 时，对应图片 Profile 的响应片段为：

```json
{
  "parameters": {
    "count": { "minimum": 1, "maximum": 2, "step": 1 },
    "quality": { "valuesMode": "suggested", "values": ["auto", "medium", "high"] }
  },
  "adapter": { "referenceSupport": { "maxCount": 3 } },
  "referenceRules": [
    { "operation": "generate", "minCount": 0, "maxCount": 0, "maxInputBytes": 0, "mimeTypes": [] },
    { "operation": "edit", "minCount": 1, "maxCount": 3, "maxInputBytes": 5242880, "mimeTypes": ["image/png"] }
  ]
}
```

以上仅展示相关字段，不是完整响应。旧配置未填写质量时保留“未确认”；支持参考图且未填写新数量字段时沿用 4 张。历史“最大输出数量”大于 4 时，实际下发与执行取 4，重新保存时需填写 1 至 4。没有新增数据库字段或迁移。

能力配置变更沿用原有版本控制：生成新的 `configVersion` 并撤销验证标记，管理员需使用本次尺寸、质量和输出数量重新完成“报价校验”；该动作不执行图片生成。客户端下次主动请求 runtime 才会取得新配置，旧版本请求沿用原有配置过期错误。

报价、提交生成及提交前复核都会检查数量上限。图片输出数量超限返回 400 `UNSUPPORTED_MEDIA_PARAMETERS`，字段为 `requestedSpec.count`；参考图数量不符返回 400 `INVALID_REFERENCE`，字段为 `referenceIds`。正常首次请求在报价、预占资金与调用上游之前被拒绝，携带现有的阶段、恢复建议和未提交、未预占状态。

## 视频时长范围配置

“系统设置 → 模型管理 → 视频”的能力表单将时长列表输入改为“最短时长（秒）”和“最长时长（秒）”。两个值必须是正整数，下限不得大于上限；相等时表示只允许该时长。帧率的后台配置与报价输入继续保留，V3 runtime 仍声明其 `support: unsupported`，上游请求仍不转发帧率。

后台 Profile 的 `capabilities` JSON 新增可选 `durationRange`，无需数据库迁移。例如设置 4 至 10 秒时保存：

```json
{
  "durationRange": { "minimum": 4, "maximum": 10 },
  "durationsSeconds": [4, 10]
}
```

其中 `durationRange` 才表示连续整数范围；原有 `durationsSeconds` 列表保留为建议值，表单保存范围时用两个端点生成此列表（上下限相等时只有一个值），不将列表 `[4, 10]` 单独解释为连续范围。范围与列表一起由表单提交，后台仍使用共享 schema 校验。

客户端下次主动调用原 runtime 接口时，视频 Profile 中时长声明为：

```json
{
  "label": "视频时长",
  "type": "integer",
  "operations": ["text-to-video", "image-to-video"],
  "support": "supported",
  "required": true,
  "valuesMode": "unknown",
  "minimum": 4,
  "maximum": 10,
  "step": 1,
  "unit": "seconds",
  "source": "profile-config",
  "confidence": "declared",
  "observedAt": null
}
```

`valuesMode: unknown` 只说明没有枚举选项，不表示数值范围未知；客户端应读取已给出的 `minimum/maximum/step`，允许 4、5、6、7、8、9、10 秒。没有配置 `durationRange` 的旧 Profile 沿用原有时长建议列表，不自动增加硬范围。编辑旧配置时，上下限初始值取原列表的最小值、最大值，管理员保存后才正式声明连续范围；管理员须确认上游确实支持区间中的时长。

自动发现的视频 Profile 允许编辑能力配置，模型标识、操作及执行方式仍由系统维护。修改时长范围沿用原有版本更新、停用与撤销验证逻辑，管理员需重新报价校验和启用。参数范围声明不代表该范围内的全部规格组合已通过真实生成验收。

报价校验规格超出范围返回 400，消息为“校验时长超出当前 Profile 配置范围”。生成报价、提交和提交前复核按同一 `durationRange` 检查，范围外返回 400 `INVALID_PARAMETER`，错误字段为 `requestedSpec.durationSeconds`，附带实际上下限、请求阶段及 `recovery: revise_request`。首次请求在上游报价、资金预占和生成之前拒绝，并标记 `submissionState: not_submitted`、`billingState: not_reserved`。缺少时长仍由原有必要规格校验报错，未改为自动填写默认值；任务查询与账务对账不新增时长范围拦截。

## 错误

仅本订阅 runtime 接口保留错误来源提供的全部可序列化业务字段：原 `message`、`code`、`errors`、嵌套 `error` 以及其他诊断信息。非 HTTP 异常使用 500，并保留原异常名称、消息及提供的诊断属性。客户端不得再用通用提示替换来源信息，也不能假定所有错误都有 `code`。

平台可补充 `statusCode/requestId/timestamp/path`；来源已有同名字段时保留来源值。HTTP 状态继续使用来源异常状态，限流保留等待字段和 `Retry-After`。客户端应保留完整响应供详情查看，按字段渲染时使用文本方式。

常见状态：未登录或企业冻结为来源 401；缺企业身份为来源 403；订阅不符合现有访问条件为 404 `Runtime unavailable`；查询参数无效为 400；限流为 429；读取和解析错误保留来源状态与诊断。企业冻结的 `ENTERPRISE_SUSPENDED` 不再被过滤器丢弃。

没有收到 HTTP 响应的断网、DNS、超时由客户端单独展示；反向代理返回 HTML 502/504 时保留实际状态和文本详情。其他业务和生成端点继续使用各自原有错误契约。

## 客户端待接入

1. 启动后获得登录身份和有效订阅时主动请求一次；设置页和 `media_get_capabilities`、`video_get_job({})` 共用同一份成功结果。
2. 展示模型名称、配置名称、参数、参考图规则和不可用原因，以 `profileId` 保存选择，生成继续使用原 `requestedSpec` 和执行接口。
3. 只在主动刷新、明确切换员工等动作中请求；关闭定时、窗口聚焦、重连、挂载刷新和通用自动重试。
4. 缓存按登录用户、企业或会话、订阅隔离；退出登录或身份变化时清空。切换员工时取消或丢弃旧响应。
5. 首次失败显示来源错误，不能伪装成空列表。已有成功结果的普通刷新失败保留上次结果和 `fetchedAt`，并标记过期；冻结、授权撤销、订阅失效或退出登录时清空或禁用缓存。
6. 不自动重试收费生成，不自动改参数或重新报价；生成阶段仍由后台检查最新授权和配置。
