# 企业共享算力余额、平均分摊与原单恢复

日期：2026-11-25。涉及 SEP 后端、SEP 管理页面及算力平台后端；价格仍由算力平台确定。此前 2026-11-23 文档描述的“公共余额不足即整笔失败、不分摊”已由本次规则替代。

## 业务规则

1. 企业算力总余额 = 未分配算力余额 + 当前成员尚未使用的企业充值余额，不包含企业钱包中未转为算力的钱、个人钱包、赠送额度。
2. 算力平台独立扣款通知到达 SEP 后，先扣未分配算力；不足部分在企业成员的企业充值余额之间平均分摊。
3. 某成员不足以支付平均份额，扣到其余额为零；剩余部分在其他有余额成员之间再次平均分摊。金额使用整数微元（人民币六位小数），尾差按成员 ID 固定排序分配。
4. 成员资金按原充值批次 FIFO 消耗，保留版本校验和批次审计。已锁定划转资金、已预占媒体资金不会重复参与分摊。
5. 不动个人钱包和赠送额度，也不会把一个企业的费用摊给其他企业。
6. SEP 正常调用仍归原调用成员；其结算通知只核对原单，不再次平均扣费。正常调用原有赠送、成员资金及自费付款顺序保持原实现。

例如公共算力 10 元，三名成员分别有 2、10、20 元，算力侧独立消费 25 元：公共扣 10 元，成员分别扣 2、6.5、6.5 元，剩余总余额 17 元。

## 跨平台并发与资金不足

两个数据库之间不建立跨库事务，不为对话新增发送前资金预占。事务锁和幂等性保证本地账务不超扣、不重复入账；跨平台采用持久原单、通知和补拉完成恢复。

### 算力平台余额不足

- SEP 发送已确认的最终结算决定时，算力侧在锁定企业余额的事务内检查余额。
- 余额不足，将原决定保存到 `sep_pending_settlements`，记录原执行、结算编号、不可变请求哈希及金额，再返回 `409 / INSUFFICIENT_PAID_FUNDS`。
- 保留整单原子扣款。例如需付 30 元、余额 20 元：待结算金额是 30 元，缺口是 10 元，本次实际扣款为 0 元。不会把部分扣款误报为完整成功。
- 算力侧后台按企业待结算顺序尝试结清；SEP 也继续重试同一结算编号。并发重试共用原幂等约束，最终只写一份结算及对应流水。
- 充值后处理原账单，绝不再次生成、重新计价或创建新结算编号。
- 新生成请求遇到企业已有欠费时返回 `ENTERPRISE_BILL_OUTSTANDING`；已有账单查询、模型查询、报价和原单结算仍可使用。已执行的免费费用单仍可免扣款结算。

### 算力已经扣款、SEP 资金分配暂时不足

- 已验证的通知先写收件记录，余额扣减、成员分摊、缺口与审计在同一个 SEP 事务中提交。
- 若公共余额和所有成员资金都用尽，未覆盖部分存入原事件的 `outstandingCny`。事件记为 `APPLIED`，表示这项扣款及其未覆盖责任均已登记，不表示所有资金缺口已消失。
- 继续推进事件水位，避免后面的充值通知被前面的缺口永久卡住。直接在算力侧充值时，通知金额优先填补旧缺口，剩余部分才增加 SEP 公共算力余额。
- 从 SEP 划入资金、成员补充企业资金或媒体原预占释放后，补拉工作会再次处理原缺口；先用公共资金，再按同一平均规则使用成员企业资金。恢复记录关联原事件，不再次向算力侧扣款。
- 事件仍有缺口时，新增生成暂缓，企业删除也会被现有账务保护阻止。

### SEP 原调用本地欠费

- 原 `UNPAID` 对话账单由费用后台工作恢复，锁定原用户及企业，并校验执行、最终费用单、用量金额和结算金额守恒。
- 只从原成员的企业资金补扣；没有成员归属的原调用从公共算力补扣。不自动拿其他成员的钱补 SEP 原调用欠费，也不自动消耗新的个人钱包或赠送额度。
- 更新同一用量及同一结算决定，补足后投递原结算任务。已投递过的结算决定不能在这条恢复路径中改写。

### 并发边界

不预占就不能保证多个已经同时发送的请求最终费用一定小于发送时余额。费用确认后可能出现欠费。本次保证余额不被扣成负数、欠费不丢失、发现欠费后暂停新增生成，以及补款后恢复原账务。暂停是企业级保守策略，可能暂停最终会免费的新生成；并不把免费额度当付费扣款。

媒体原有报价预占、超出报价时的 `RECONCILING` 流程沿用现有实现；本次没有新增对话预占，也没有改写视频生成流程。

## 接口与展示

余额通知、签名、事件编号、事件序号和原结算请求格式保持现有协议。

| SEP 接口或字段 | 内容 |
| --- | --- |
| `GET /api/enterprise/compute-integration` 的 `funds` | 企业管理员查看算力余额构成及欠费 |
| 平台企业连接列表/详情的 `funds` | 平台管理员查看同一组余额 |
| `GET /api/admin/compute-integrations/:enterpriseId/balance-sync/funds` | 受管理员权限保护的余额汇总接口 |
| 原余额同步状态的 `events[].outstandingCny` | 当前仍未覆盖的原事件金额 |
| 原余额同步状态的 `events[].allocation` | 原分摊规则、公共扣款、成员及批次明细 |

`funds` 中的金额均为人民币六位小数字符串，另含状态与快照信息：

| 字段 | 含义 |
| --- | --- |
| `totalBalanceCny` | 本地未分配资金与成员剩余企业资金合计 |
| `unallocatedCny` | 公共算力账面余额；其中待划转锁定部分不可用 |
| `memberBalanceCny` | 成员企业充值剩余资金合计；已预占媒体资金已扣出 |
| `syncShortfallCny` | 算力独立扣款通知已登记、SEP 尚缺的本地资金 |
| `localUnpaidCny` | SEP 原对话尚未补足的本地费用 |
| `pendingSettlementCny` | 本地已确认付款、等待算力侧确认的付费金额 |
| `remoteAvailableCny` / `remoteFrozenCny` | 最近一条已应用通知携带的算力侧余额快照，可为空 |
| `sequence` | 上述远端通知快照的流水水位，不保证是算力侧此刻最新余额 |
| `generationPaused` | 是否因本地欠费、待处理事件或远端拒绝结算暂停新增生成 |

这些项目描述不同处理阶段，不要简单相加当成“总欠费”，也不要把远端快照和本地总余额混为同一时间点的数值。企业及平台的连接详情展示余额构成和欠费提示。分摊、后续补扣的审计分别保存在 `compute_balance_event` / `compute_balance_recovery` 钱包流水元数据中。
