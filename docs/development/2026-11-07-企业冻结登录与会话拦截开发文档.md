# 企业冻结登录与会话拦截开发文档

日期：2026-11-07

## 背景与目标

运营端已有企业冻结/解冻操作。产品目标已确认：企业被冻结后，该企业的所有成员都不能登录 Web 平台或桌面客户端，也不能继续使用冻结前签发的会话；平台管理员仍可登录并处理该企业。解冻后不需要逐个恢复成员账号，成员可重新登录。

本文件先记录冻结行为的调研和验收约定，后续“实现结果”一节跟踪按本方案落地的代码。本文档当前对应的开发已完成针对性实现与单测验证，尚未执行真实数据库 E2E 或部署验证。

## 当前实现与缺口

1. `AdminService.suspendEnterprise()` 只向 `Enterprise.metadata` 写入 `suspended: true`、冻结原因、冻结时间和操作人；解冻只将 `suspended` 设为 `false`。该字段没有被认证流程读取，也没有撤销成员会话。
2. Web 密码登录在 `AuthService.login()` 中只校验 `User.status`；OAuth 回调最终调用 `loginWithUser()`，同样只校验用户状态。Web refresh 只校验用户状态和 refresh session。
3. 桌面端有独立的 `ClientService.login()`、`refreshAccessToken()` 和 `refreshInstanceToken()`。这些入口也只校验用户状态、设备和订阅授权，没有统一检查企业冻结状态。
4. 普通 Web/桌面 access token 由 `JwtStrategy` 调用 `AuthService.validateUser()` 校验用户。该校验只查询 `User.status`，也没有统一确认 JWT 中的 `sid` 仍对应有效 session，因此冻结前签发的 access token 仍可通过大部分 `JwtAuthGuard` 路由；仅撤销 refresh session 本身不足以让这些无状态 JWT 立即失效。
5. `SessionService.assertActiveSession()` 检查 session、账号和设备状态，不检查企业。桌面 employment token 的 `ClientEmploymentGuard` 会调用该方法，因此冻结后已签发的 employment token 仍可能有效。
6. 通知 WebSocket 只在认证消息到达时调用 `AuthService.validateUser()`；连接建立后仅处理 ping，不会再次检查账号或企业状态，冻结后可能继续保持连接并接收推送。
7. 企业业务上下文按 `Enterprise.status = ACTIVE` 过滤，但当前运营端冻结不改变该字段。冻结与企业关闭是两个不同状态。

因此目前冻结主要是运营端展示、筛选和统计标记，不会阻止成员登录或使用现有会话。管理页面“冻结后该企业将无法使用平台服务”的提示与后端实际行为不一致。

## 冻结语义

### 冻结后立即生效

- 企业所有成员不能通过 Web 密码或 OAuth 登录。
- 企业所有成员不能通过桌面客户端密码登录。
- Web、桌面 access token、refresh token 和 employment token 均不能继续用于认证或续期。
- 已连接的通知 WebSocket 应断开，断开前不得继续推送冻结后产生的新通知。
- 企业成员不能通过未显式检查冻结状态的业务接口继续发起新操作；认证入口与企业业务上下文都必须有统一的服务端拦截。
- 平台管理员不受企业冻结影响，仍能访问平台管理端、查看冻结详情并解冻。

### 冻结不代表

- 不把成员 `User.status` 改成禁用，不删除用户、membership、订阅或企业数据。
- 不等同于关闭企业。关闭仍使用 `Enterprise.status = CLOSED`，其不可逆/账户清理语义继续独立管理。
- 不自动取消已受理的异步任务、不撤回已完成数据、不退款或改写账务。冻结生效后拒绝新请求；冻结前已受理的任务按既有状态机完成或失败，并照常对账结算。
- 不向普通成员展示运营内部填写的完整冻结原因。登录提示使用统一文案并给出联系管理员的指引；运营端仍可查看原因。

### 解冻

将企业冻结标记解除后，原成员账号仍保持原状态。成员重新登录后恢复使用；冻结期间被撤销的 session 不恢复，也不恢复旧 refresh token。冻结动作需撤销成员全部 Web/Desktop sessions，并让普通 access token 的校验同时检查 `sid` 对应 session 是否仍有效。这样旧 access token 在解冻后也不会因 JWT 尚未过期而重新生效。

## 推荐实现方案

### 冻结状态来源

第一阶段继续复用现有 `Enterprise.metadata.suspended` JSON 字段，不新增字段或迁移，避免引入重复状态。集中封装读取逻辑，不能在多个模块各自解析 JSON。

封装一个可被认证模块和企业模块调用的企业访问策略，例如 `EnterpriseAccessService`，负责：

- 依据用户 membership 查询所属企业及 `status`、`metadata.suspended`。
- 按单企业 MVP 规则检查用户所属企业。没有企业 membership 的普通用户不因“没有企业”而被误拒绝。
- 平台管理员 (`PLATFORM_ADMIN` / `SUPER_ADMIN`，以当前实际角色判断为准) 通过企业冻结检查；不能因为登录用户有企业 membership 就把平台管理员一并挡住。
- 企业不存在、membership 不存在、企业 CLOSED、企业 suspended 的结果清晰区分。企业 CLOSED 沿用现有业务错误；企业 suspended 返回统一认证拒绝。
- DB 查询失败时失败关闭并返回服务不可用，不得当成未冻结放行。

当前注释和业务实现按“一个用户只属于一家企业”运行。若启用多企业 membership，需先定义用户同时属于冻结企业和正常企业时的会话/租户选择语义，再调整查询规则；不可继续静默取第一条关系并假定冻结范围。

### 认证入口和已有令牌

| 入口/凭据 | 当前校验位置 | 开发要求 |
| --- | --- | --- |
| Web 密码登录 | `AuthService.login()` | 密码校验成功、创建 Web session 前调用企业访问策略；冻结成员拒绝登录，不签发 token/cookie。 |
| Web OAuth 登录 | `AuthService.loginWithUser()` | 统一复用相同策略；覆盖所有 OAuth provider 的 callback，不允许只在密码登录拦截。 |
| Web refresh | `AuthService.refresh()` / `SessionService.rotateRefreshToken()` | refresh 的预校验和实际轮换均检查企业状态；冻结时不轮换 token，不返回 access token。 |
| 桌面密码登录 | `ClientService.login()` | 在创建设备 session 前校验；冻结成员不得创建 session 或返回任一 token。避免留下仅为登录尝试而创建的设备记录。 |
| Web/桌面 access token | `JwtStrategy.validate()` → `AuthService.validateUser()` | 在统一校验中同时检查用户状态、JWT `sid` 对应 session 有效性和企业冻结，覆盖使用 `JwtAuthGuard` 的 Web 和桌面普通接口。冻结时即使 JWT 未过期也拒绝；平台管理员及无企业用户按上述规则处理。 |
| 桌面 refresh | `ClientService.refreshAccessToken()` / `SessionService` | 共享 session 企业状态校验；失败时不返回或轮换 token。 |
| Employment token 签发 | `ClientService.refreshInstanceToken()` | 签发前确认用户 session 与 token 所属企业均未冻结，不能只依赖原订阅仍 ACTIVE。 |
| 已签发 employment token | `ClientEmploymentGuard` → `SessionService.assertActiveSession()` | 每次请求检查 session 用户企业冻结状态，并核对 token 的 `enterpriseId` 仍与有效 membership/订阅归属一致；冻结后立即拒绝。 |
| 通知 WebSocket | `NotificationsGateway` 调用 `AuthService.validateUser()` | 新连接自然被拒绝；已认证连接需提供冻结时按 userId 关闭连接的路径，或在每次消息/推送前重新校验。优先在冻结动作后主动关闭该企业成员连接，避免冻结后仍收到通知。 |

以上规则的权威检查必须位于后端。前端清除状态和跳转登录页只负责体验，不能代替后端拦截。

### 冻结/解冻操作与 session 撤销

冻结事务至少要保证：企业冻结标记提交后，新登录、refresh、access token 验证均立即拒绝。随后批量撤销该企业全体成员的 Web/Desktop sessions 和 refresh tokens，普通 JWT 校验必须读取 `sid` 对应的 session 状态，不能只校验用户 ID。撤销原因使用稳定值，例如 `enterprise_suspended`，便于审计排查。建议冻结状态更新和 session 撤销在同一数据库事务内完成，或以可重试的事务/任务保证撤销完成；撤销失败时不能向运营端返回“冻结成功”。

冻结与登录并发时以企业冻结提交后的状态为准：并发登录即使先得到 token，也必须在后续每次请求及 session 校验中被拒绝。创建 session 的路径要做最终企业状态校验，避免冻结已提交后仍成功创建可用 session。

解冻仅清除冻结状态、记录解冻人和时间，不恢复已撤销 session。解冻与登录并发时，冻结标记提交后的状态决定是否允许新 session。

审计记录建议覆盖操作者、企业、原因、冻结/解冻时间、受影响成员数、撤销 session 数及失败结果。原因不进入普通认证错误响应。

### 错误与前端行为

- 密码登录、OAuth callback、桌面登录对冻结企业返回可理解的统一错误，例如“所属企业已被冻结，暂无法登录，请联系平台管理员”。不得返回数据库字段名或内部栈信息。
- 已登录用户后续请求使用 401（凭据当前无效），错误标识建议稳定为 `ENTERPRISE_SUSPENDED`，前端据此清除内存 access token、用户态和企业态，清除/废弃本地 refresh 凭据，并回到登录页展示冻结提示。不能把所有 401 一概当作冻结。
- 对 OAuth 回调，要确保失败分支不留下 refresh cookie/session；错误页面从 callback 参数读取稳定错误码，不直接拼入内部冻结原因。
- 桌面端按相同错误码清除安全存储的 refresh token 和内存 access token，并退出到登录状态。
- 若冻结后用户请求进行中，已开始的外部模型调用/异步任务无法可靠撤销；不得向用户承诺回滚已发出的上游请求。新的任务创建和新的模型调用必须被拒绝。

## 代码影响面

预期实现时检查或修改以下位置，最终以实现时的实际依赖注入结构为准：

- `backend/src/modules/admin/admin.service.ts`：冻结/解冻事务、批量撤销成员 session、记录审计结果。
- `backend/src/modules/auth/auth.service.ts`、`oauth.service.ts`：Web 密码、OAuth、refresh 与统一 access token 验证。
- `backend/src/modules/auth/session.service.ts`：session 创建、refresh 轮换和 access JWT 的 `sid` 校验对企业冻结的共同约束；批量按企业撤销 session 的方法。
- `backend/src/modules/client/client.service.ts`、`client-employment.guard.ts`：桌面登录/refresh、employment token 签发与使用。
- `backend/src/modules/notifications/notifications.gateway.ts`：已连接通知 WebSocket 的失效处理。
- `backend/src/modules/enterprise/`：集中企业冻结判定；`EnterpriseContextService.resolve()` 可作为企业业务资源的统一拒绝点，但需保留平台管理员受限绕行的既有规则。
- 相关 controller/DTO 与前端登录错误处理：只在需要呈现稳定错误码时调整响应契约。

原则上不需要 Prisma schema migration。若实现发现 JSON metadata 无法满足查询性能或并发约束，再单独提出迁移，不在本方案中预设新增字段。

## 验收标准

1. 冻结企业成员使用正确密码登录 Web 和桌面端均失败，不创建有效 session，不返回 access/refresh token。
2. 冻结企业成员使用 OAuth 登录失败；无 refresh cookie 或有效 session 被残留。
3. 冻结前获得的 Web/桌面 access token、Web/桌面 refresh token、employment token 在冻结后均无法访问受保护接口、续期或调用员工执行接口。
4. 冻结前已连接的通知 WebSocket 被关闭，之后不再收到推送。
5. 平台管理员冻结企业后仍能访问运营端、查看冻结信息并解冻；平台管理员自己的登录 session 不被批量撤销。
6. 无企业归属的普通用户登录行为不变；企业关闭的现有语义不被误改为“冻结”。
7. 解冻后成员可以重新登录并获得新 session；冻结前已撤销的 refresh token 不可复用。
8. 冻结不会修改成员账号状态，不会删除数据，不会自动取消/退款冻结前已受理任务；冻结后新建业务被拒绝。
9. 冻结写入成功但 session 撤销失败时，管理接口不能错误地报告全部完成；重试行为幂等。
10. 数据库/策略查询故障不会导致放行；普通成员的错误信息不泄露内部冻结原因。

## 测试建议

### 单元测试

- 企业访问策略：冻结/未冻结、关闭、无 membership、平台管理员、数据库异常、多 membership 约束。
- `AuthService`: 冻结成员密码登录、OAuth 登录、refresh 和 `validateUser` 均拒绝；不冻结用户行为保持原样。
- `ClientService`: 桌面登录、refresh、employment token 签发分别拒绝冻结成员；拒绝前不创建 session、不轮换 refresh token。
- `SessionService`: access JWT 的 `sid` 校验、refresh 预校验/轮换和 session 创建都覆盖冻结状态；session 批量撤销只影响目标企业成员，解冻后旧 JWT/refresh token 均不能复活。
- `ClientEmploymentGuard`: 冻结后旧 employment token 被拒绝，且不改变原有非法 token 和服务不可用错误语义。
- `AdminService`: 冻结事务更新状态并撤销成员 session；重复冻结、重复解冻沿用明确错误；撤销失败不伪报成功。
- `NotificationsGateway`: 冻结成员已有连接关闭、移出在线客户端集合，后续 push 不发给该连接。

### HTTP/E2E

建立一个企业、企业管理员/成员、平台管理员和无企业用户。分别在冻结前获取 Web、桌面、refresh、employment token 并连接通知 WebSocket；执行冻结后逐一验证续期和受保护请求均被拒绝、WebSocket 已断开、平台管理员不受影响。随后解冻并验证成员可用新登录建立 session，但旧 refresh token 仍被拒绝。

测试必须使用 mock Prisma/session 的单元测试和隔离的 HTTP 测试，不连接或修改开发/生产数据库。至少包含一条冻结与登录/refresh 并发测试，确保最终状态由冻结标记决定。

## 实施顺序

1. 编写并测试企业冻结访问策略，定义错误码与角色绕行规则。
2. 接入普通 access token 校验和 `SessionService`，先确保已有 Web/桌面 token、refresh、employment token 会失效。
3. 接入 Web 密码、OAuth、桌面登录及 token 签发入口，阻止冻结后创建 session。
4. 调整运营端冻结/解冻为可审计、可重试的事务，并撤销目标企业全部成员 session。
5. 处理已建立的通知 WebSocket，接入前端 Web 和桌面端冻结错误体验。
6. 补齐单元及 HTTP/E2E 测试，运行后端相关 Jest、前端相关测试和 TypeScript 检查；按影响面运行构建或 smoke。
7. 对照验收标准检查运营页面文案与后端实际结果一致，再部署后验证冻结/解冻闭环。

## 实现结果（2026-11-07）

- `SessionService` 提供统一企业冻结检查；登录 session 创建时在事务内对企业行加共享锁并再次检查，冻结事务则锁定企业行、更新冻结标记并批量撤销成员 sessions 和 refresh tokens。
- Web 密码/OAuth 登录、Web refresh、桌面密码登录和桌面 refresh 都会经过冻结校验。access JWT 现在要求包含有效 `sid`，每次请求检查 session、账号、设备和企业冻结状态；解冻不会恢复已撤销 session。
- 桌面 employment token 签发前检查订阅所属企业状态，使用 token 的请求检查 session 与企业冻结状态。企业业务上下文检查冻结标记；数据库读取失败时返回服务不可用，不按“未冻结”放行。
- 冻结成员连接通知 WebSocket 时会被拒绝；冻结事务提交后立即主动关闭本进程中目标成员的已认证通知连接，平台管理员被排除。连接存续期间的心跳和推送仍会重新验证 session，失效后关闭连接。多进程部署下跨进程连接关闭仍需广播机制，当前每次推送前的认证检查继续阻止失效会话接收通知。
- Web OAuth callback 展示冻结提示；Web API 收到稳定错误码 `ENTERPRISE_SUSPENDED` 时清理内存认证态并将错误交给登录流程展示。
- 平台管理员（当前系统角色 `ADMIN`）及无企业归属用户不因企业冻结检查被误拒绝；冻结不修改用户状态。未新增数据库字段或迁移。
- AdminService 的冻结和解冻使用事务与企业行锁；冻结标记和 session/token 撤销处于同一事务，撤销异常会回滚而不会报告成功。

验证：后端相关 Jest 8 个套件、213 项测试通过；Web API 客户端测试 33 项通过；后端与 Web TypeScript 检查通过。需补做使用隔离数据库的 HTTP/E2E 并发验证，以及部署环境的冻结、解冻闭环验证。桌面客户端如何消费冻结错误并清除其安全存储凭据，需结合桌面客户端仓库/实现另行验证；当前后端会拒绝其后续请求。
