## 已确认的问题

### F01：混合结算完成，但余额同步永久停在原流水前（P1）

责任边界：双方结算回执与事件匹配规则不一致，需要统一；SEP 当前匹配条件直接触发失败。

复现：

1. 为新企业充值算力 50 元，分配成员 1 元，将本次免费额度设置为 0.000001 元。
2. 真实对话的最终费用为 0.000095 元，其中免费 0.000001 元、付费 0.000094 元。
3. 两边结算已完成，SEP 结算状态为 `COMMITTED`。
4. 算力生成付费流水序号 2、免费流水序号 3；结算回执返回 `sequence="3"`。
5. SEP 把 3 保存为结算的 `remoteSequence`，却要求付费事件的序号也等于 3，因此拒绝真实的序号 2。

实际错误：`COMPUTE_EVENT_ORIGINAL_SETTLEMENT_PENDING`。本地通知水位停在 1，付费事件保留为 `RECEIVED`，后续通知无法继续。

执行编号：`cmwspn2uu00hfvf74v0vapnmu`。

代码位置：

- SEP：`backend/src/modules/compute-integration/compute-balance-sync.service.ts:110`，付费事件按相同序号匹配，免费事件按该序号加一匹配。
- SEP：`backend/src/modules/compute-integration/compute-integration.worker.ts:129`，保存回执序号。
- 算力：`D:/github/LongdaoAI-worktree-one/backend/internal/service/sep_ledger.go:231`，混合结算把回执序号改为最后一条免费流水的序号。

修复方向：明确回执 `sequence` 是首条流水号还是结算结束水位，统一双方实现；分别校验付费、免费流水的编号和序号。补充“混合结算后再充值”的回归，不能仅以结算 `COMMITTED` 为验收标准。

### F02：外部扣款遇到公共资金不足后，后续充值也无法恢复同步（P1）

责任边界：SEP 的入账限制与两边共享余额的使用范围存在冲突，需要双方补齐恢复规则。

复现：

1. 算力后台给企业加 2 元，SEP 同步为公共算力资金 2 元。
2. SEP 把全部 2 元分配给成员，公共资金为 0，算力总余额仍为 2 元。
3. 算力后台扣 1 元，远端成功；SEP 因公共资金不足拒绝应用该事件。
4. 算力后台再加 1 元，远端余额恢复为 2 元，但 SEP 仍先处理上一条扣款并失败，无法应用后面的充值。

实际错误：`COMPUTE_PUBLIC_FUNDS_INSUFFICIENT`。远端水位为 3，本地水位为 1。成员仍持有 2 元，公共资金为 0；没有重复扣成员资金，但通知队列被阻塞。

代码位置：

- `backend/src/modules/compute-integration/compute-balance-sync.service.ts:80` 附近，外部扣款只减少公共钱包，不允许公共资金为负。
- 同文件 `apply()` 要求连续序号，`sync()` 在首个失败事件停止。
- 成员算力接口提供设置额度和追加资金，当前没有针对这一冲突的完整处置流程。

修复方向：约定算力侧独立消费可使用哪些 SEP 资金，以及公共资金不足时如何记录待弥补负债或协调资金来源。恢复必须保留原扣款、充值和审计关联，不能人工跳水位、改余额或直接认定原扣款未发生。

### F03：删除保护看不到尚未到达的远端充值（P1）

责任边界：SEP 删除保护，且需要算力侧提供关闭账户或禁止新变账的配合机制。

使用真实本地事务锁住企业，阻止充值通知落库；在算力后台给该企业充值 0.1 元，再调用删除流程使用的 `hasOpenAccounting()`：

- 充值前：返回 `false`。
- 算力已充值、通知尚未入 SEP：仍返回 `false`。
- 同时查询算力余额：0.100000 元、流水水位 1。

没有执行实际删除。释放事务锁并同步后，0.1 元正常入 SEP。

代码位置：

- `backend/src/modules/compute-integration/compute-integration.service.ts:163`，检查本地任务、结算和已收到事件，不查询或关闭远端账户。
- `backend/src/modules/admin/enterprise-deletion-cleanup.service.ts:35`，使用上述结果决定是否存在算力账务阻塞。

修复方向：删除前进入关闭流程，远端停止新调用和新变账，拉齐确定水位并核对余额、冻结额和未结算任务，再执行本地删除。仅增加一次远端余额查询仍会有“查完后又充值”的竞态。

## 网关回归风险

F07（P2）：异常 SSE 的 `[DONE]` 早于错误事件。

网关 HTTP 回归以测试上游返回“有 usage、无 finish_reason，随后发送 `[DONE]`”复现。实际 HTTP 200 输出先出现 `[DONE]`，之后才出现 `event: error`、`UPSTREAM_INCOMPLETE_STREAM`。在 `[DONE]` 停止读取的客户端可能把该异常当成成功完成。

位置：`backend/src/modules/gateway/gateway.controller.ts:204` 附近，先转发原 chunk，再在 EOF 校验完整性并追加错误事件。

修复方向：统一成功结束与失败结束的顺序，完整性校验失败时，不能在已经发出成功终止信号后才通知错误。该风险来自真实 controller 的 HTTP 测试与源码核对，本轮未向真实供应商制造故障。
