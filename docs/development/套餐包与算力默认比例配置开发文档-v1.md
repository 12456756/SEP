# 套餐包与算力默认比例配置开发文档

## 1. 文档目标

本文档用于实现“套餐包”能力：平台运营预先配置一组数字员工，企业以一个套餐价格批量购买；套餐履约后，系统为企业创建多条员工订阅，并按照员工级算力规则分别发放赠送算力。

本文档同时明确订阅赠送算力的默认比例配置，默认比例放在平台管理端“系统设置 → 计费与额度”中维护。第一版采用固定套餐、购买后立即生效、员工级算力，不实现用户自由组合、套餐库存和共享算力池。

## 2. 当前实现基线

当前系统已经具备套餐化所需的支付和履约基础：

- `Subscription` 表示企业与数字员工之间的雇佣关系，同一企业对同一员工只有一条订阅记录。
- `Order` / `OrderItem` 支持一个订单包含多个数字员工。
- `OrderService.fulfill()` 在事务内更新订单、创建订阅、自动授权购买管理员并发放订阅赠送算力。
- `SubscriptionFulfillmentService` 是订阅履约的统一入口，直接订阅和市场订单共用同一套逻辑。
- `SubscriptionCredit` 是员工级赠送算力账本，算力只用于对应员工。
- `EnterpriseWallet` 是企业人民币钱包，企业充值和对话扣费已经有独立账本。
- 系统设置已经存在以下配置：
  - `DEFAULT_EMPLOYEE_GIFT_PERCENTAGE`：订阅赠送算力默认比例，当前默认值为 `10`。
  - `DEFAULT_EMPLOYEE_GIFT_CNY`：固定默认赠送算力金额。
- 员工模板已经支持 `includedComputeCNY`，其中 `null` 表示未配置，`0` 表示明确不赠送，大于 `0` 表示员工级固定金额覆盖。

实现时应优先扩展这些现有能力，避免新增第二套支付、订单或算力扣减链路。

## 3. 产品决策

### 3.1 套餐形态

第一版为平台预先定义的固定套餐：

```text
套餐 A
  - 数字员工 A，12 个月
  - 数字员工 B，12 个月
  - 数字员工 C，12 个月
  - 套餐售价：平台运营手动设置
```

第一版不支持企业在购买页临时增删员工，也不支持一个套餐内重复购买同一员工。

### 3.2 套餐购买后的归属

支付成功后，套餐内所有员工立即创建或复活为企业订阅。购买套餐的企业管理员默认获得全部员工的使用权，其余成员仍通过现有授权流程获得使用权。

第一版不做“套餐库存”“先购买后分配”。如果未来要支持库存，应新增权益库存模型，不能把未分配员工伪装成已经激活的 `Subscription`。

### 3.3 套餐定价

套餐售价由平台运营人员手动填写，不由系统自动计算。系统需要同时展示员工原价合计和套餐售价，便于运营确认折扣：

```text
员工原价合计 = 套餐项年费 × 套餐项周期 / 12 的总和
套餐优惠金额 = max(员工原价合计 - 套餐售价, 0)
```

运营端可以设置低于、等于或高于员工原价合计的价格，但发布时建议默认限制为不高于原价合计；如果后续确实需要溢价套餐，应由产品明确允许并增加原因字段。

### 3.4 员工级算力

第一版采用员工级算力。套餐不创建一笔可跨员工共享的算力余额，而是将套餐内每个员工的赠送算力分别发放到对应的 `SubscriptionCredit`。

员工赠送算力解析优先级如下：

```text
员工级 includedComputeCNY（明确填写，包括 0）
  > 系统默认比例 × 员工年费
  > 固定默认赠送金额
```

具体语义：

- `includedComputeCNY = null`：使用系统默认规则。
- `includedComputeCNY = 0`：明确不赠送，不能回退到 10%。
- `includedComputeCNY > 0`：使用该员工固定金额。
- 系统默认比例大于 0 且员工有年费时：赠送 `年费 × 比例 / 100`。
- 系统默认比例为 0，或员工没有有效年费时：使用固定默认赠送金额。

套餐创建订单时必须把每个套餐项最终生效的赠送金额写入订单快照。支付后不能重新读取员工当前配置，否则运营修改配置会影响已下单订单。

## 4. 系统设置设计

### 4.1 设置项

沿用现有 `SystemSetting` 通用设置机制，不新增独立配置表。

| Key | 展示名称 | 类型 | 默认值 | 范围 | 说明 |
|---|---|---:|---:|---:|---|
| `DEFAULT_EMPLOYEE_GIFT_PERCENTAGE` | 订阅赠送算力默认比例 | number | `10` | 0-100 | 员工未配置固定金额时，按年费比例计算 |
| `DEFAULT_EMPLOYEE_GIFT_CNY` | 订阅赠送算力固定默认值 | number | `0` | >=0 | 比例无法生效时使用 |

当前配置已经位于“系统设置 → 计费与额度”，前端需要保留该位置，并补充以下说明：

```text
员工未单独配置固定赠送金额时，按员工年费 × 默认比例计算。
默认比例为 0 或员工没有有效年费时，使用固定默认值。
配置只影响之后创建的新订阅和新套餐订单，不追溯已有订阅、已支付订单和历史算力账单。
```

### 4.2 校验规则

- 默认比例必须是有限数字，范围 `0 <= value <= 100`。
- 固定默认金额必须是有限非负金额，最多保留两位小数。
- 空字符串表示删除数据库覆盖，回退到环境变量或代码默认值，沿用现有设置行为。
- 设置更新成功后，只影响后续订单和订阅履约。
- 不修改已创建订单中的 `includedComputeCNY` 快照。

### 4.3 计算示例

当默认比例为 10% 时：

```text
员工年费 ¥5,000 -> 赠送 ¥500
员工年费 ¥8,888 -> 赠送 ¥888.80
```

金额统一使用 Decimal 计算并保留 6 位账务精度，展示层按人民币金额格式化。员工套餐订单明细字段可以保留两位小数，但写入 `SubscriptionCredit` 时仍经过现有金额归一化逻辑。

## 5. 数据模型设计

### 5.1 套餐模型

建议新增 `EmployeeBundle` 和 `EmployeeBundleItem`，不要复用 `EmployeePackage`。当前 `EmployeePackage` 表示员工运行包（ZIP/npm/git 制品），与商业套餐是不同领域概念。

```prisma
enum EmployeeBundleStatus {
  DRAFT
  PUBLISHED
  ARCHIVED
}

model EmployeeBundle {
  id           String              @id @default(cuid())
  code         String              @unique
  name         String
  description  String?             @db.Text
  cover        String?
  status       EmployeeBundleStatus @default(DRAFT)

  /// 平台运营手动设置的套餐成交价
  priceCNY     Decimal             @db.Decimal(12, 2)
  periodMonths Int                 @default(12)

  publishedAt  DateTime?
  createdAt    DateTime            @default(now())
  updatedAt    DateTime            @updatedAt

  items        EmployeeBundleItem[]
  orders       Order[]

  @@index([status, publishedAt])
  @@map("employee_bundles")
}

model EmployeeBundleItem {
  id                 String          @id @default(cuid())
  bundleId           String
  employeeId         String

  /// 第一版与套餐周期一致，保留字段便于未来支持不同周期
  periodMonths       Int             @default(12)

  /// 可选的套餐项算力覆盖。null 表示沿用员工与系统默认规则。
  includedComputeCNY Decimal?        @db.Decimal(12, 2)

  bundle             EmployeeBundle @relation(fields: [bundleId], references: [id], onDelete: Cascade)
  employee           DigitalEmployee @relation(fields: [employeeId], references: [id], onDelete: Restrict)

  @@unique([bundleId, employeeId])
  @@index([employeeId])
  @@map("employee_bundle_items")
}
```

说明：`EmployeeBundleItem.includedComputeCNY` 建议保留，但第一版后台可以不开放编辑，默认使用员工级配置解析结果。保留该字段可以支持未来“套餐专属赠送算力”而不需要再次改表。

### 5.2 订单扩展

现有 `Order` 是员工订阅订单。建议增加订单类型和套餐关联：

```prisma
enum OrderType {
  EMPLOYEE
  BUNDLE
}

model Order {
  // 现有字段保留
  orderType OrderType @default(EMPLOYEE)

  bundleId  String?
  bundle    EmployeeBundle? @relation(fields: [bundleId], references: [id], onDelete: SetNull)

  /// 下单时的套餐快照
  bundleName         String?
  bundlePriceCNY     Decimal? @db.Decimal(12, 2)
  bundlePeriodMonths Int?
}
```

`OrderItem` 增加快照字段：

```prisma
model OrderItem {
  // 现有字段保留
  employeeVersion    String?
  purchaseAmountCNY  Decimal? @db.Decimal(12, 2)
  fulfilledSubscriptionId String? @unique
}
```

订单创建时必须快照以下内容：

- 套餐名称、套餐编码和套餐售价；
- 员工 ID、员工名称、员工模板版本；
- 员工周期和购买金额；
- 每个员工最终赠送算力金额；
- 套餐项是否覆盖了员工默认赠送规则。

已支付订单不能依赖当前套餐表或当前员工表重算权益。

### 5.3 企业关系

`Enterprise` 增加：

```prisma
bundles EmployeeBundle[] @relation("BundleOrders")
```

如果 Prisma 关系命名导致现有 `Order` 关联冲突，使用显式关系名，例如 `OrderBundle`。不建议在企业表直接增加套餐余额或套餐库存字段。

## 6. 后端模块设计

### 6.1 新增模块

建议新增：

```text
backend/src/modules/employee-bundle/
  employee-bundle.module.ts
  employee-bundle.controller.ts
  employee-bundle.service.ts
  employee-bundle.dto.ts
  employee-bundle.service.spec.ts
```

职责边界：

- 套餐 CRUD、发布、下架；
- 套餐项校验；
- 市场端套餐查询；
- 企业端套餐订单创建所需的套餐快照构建；
- 不负责支付回调；
- 不直接创建订阅；订阅创建仍由 `SubscriptionFulfillmentService` 负责。

### 6.2 运营端接口

```text
POST   /admin/employee-bundles
GET    /admin/employee-bundles
GET    /admin/employee-bundles/:id
PATCH  /admin/employee-bundles/:id
POST   /admin/employee-bundles/:id/publish
POST   /admin/employee-bundles/:id/archive
```

创建/更新请求示例：

```json
{
  "code": "ECOMMERCE_STARTER_2026",
  "name": "电商运营起步套餐",
  "description": "适合电商团队的运营、客服和数据分析员工组合",
  "priceCNY": 8800,
  "periodMonths": 12,
  "items": [
    { "employeeId": "employee-1" },
    { "employeeId": "employee-2" },
    { "employeeId": "employee-3" }
  ]
}
```

发布前校验：

- 套餐至少包含一名员工；
- 员工 ID 不重复；
- 所有员工处于 `APPROVED`；
- 员工存在有效年费；
- 套餐价格大于 0；
- 周期在允许范围内，例如 1、3、6、12、24、36 个月；
- 套餐项的最终价格和赠送算力可以被稳定计算。

### 6.3 市场端接口

```text
GET /marketplace/bundles
GET /marketplace/bundles/:id
```

返回内容至少包括：

- 套餐基本信息；
- 套餐售价；
- 员工原价合计；
- 优惠金额和优惠比例；
- 套餐员工清单；
- 每个员工的赠送算力；
- 套餐总赠送算力；
- 当前发布状态。

市场接口展示的是当前套餐配置，订单接口创建时重新读取并校验，不能信任前端传入的价格或算力。

### 6.4 企业端订单接口

```text
POST /orders/bundles/:bundleId
POST /payment/alipay/create
POST /payment/orders/:id/balance-pay
GET  /orders
GET  /orders/:id
```

创建套餐订单时只接收 `bundleId`，不接收价格、员工列表和算力金额。后端流程：

1. 解析当前用户所属企业；
2. 校验企业管理员权限；
3. 查询 `PUBLISHED` 套餐；
4. 查询套餐内所有员工；
5. 校验员工状态和企业现有订阅；
6. 计算员工原价合计、套餐售价和每项赠送算力；
7. 创建 `Order(orderType=BUNDLE)` 和订单明细快照；
8. 返回支付所需的订单信息。

如果套餐内有已处于 `ACTIVE` 的员工订阅，第一版直接拒绝整单下单，避免支付后出现部分员工无法履约。`EXPIRED`、`TERMINATED` 或 `PAUSED` 的处理需要在实现时统一定义，推荐允许重新激活但保留原模板版本提示。

## 7. 支付与履约流程

### 7.1 支付方式

套餐复用现有两种支付方式：

- 支付宝支付：通过现有 `PaymentService` 和异步通知流程；
- 企业余额支付：先扣企业钱包，再调用订单履约。

支付宝订单号继续使用现有 `ORD` 前缀，不新增套餐专用支付前缀。回调通过订单记录的 `orderType` 区分员工订单和套餐订单。

### 7.2 履约事务

扩展 `OrderService.executeFulfillment()`：

```text
开始事务
  校验订单仍为 PENDING
  校验下单人仍是企业管理员
  更新 Order = PAID
  如果 orderType = EMPLOYEE：执行现有单员工履约
  如果 orderType = BUNDLE：
    遍历 OrderItem
      调用 SubscriptionFulfillmentService.fulfill()
      写入 fulfilledSubscriptionId
  清理套餐涉及的购物车项（如果存在）
提交事务
```

每个套餐项调用：

```ts
await this.fulfillment.fulfill(tx, {
  enterpriseId: order.enterpriseId,
  employeeId: item.employeeId,
  purchaserMemberId: purchaser.id,
  displayName: item.employeeName,
  startDate: now,
  endDate,
  sourceType: 'order',
  sourceId: order.id,
  purchaseAmountCNY: item.purchaseAmountCNY?.toNumber(),
  purchasePeriodMonths: item.periodMonths,
  grantedCNY: item.includedComputeCNY.toNumber(),
});
```

### 7.3 幂等要求

以下情况必须安全：

- 支付宝重复通知；
- 主动查单与异步通知同时履约；
- 订单履约重试；
- 同一套餐订单并发支付；
- 某个员工已经被第一次履约创建，第二次重试不能重复发放算力。

现有订单状态、支付通知 `tradeNo` 唯一约束和 `SubscriptionCredit.subscriptionId` 唯一约束可以作为基础，但套餐测试必须覆盖整单重放和中途失败回滚。

## 8. 退款与订单关闭

### 8.1 未支付订单

套餐未支付时可以关闭订单，不创建任何订阅和算力记录。

### 8.2 已支付订单

第一版只支持整单退款，不支持套餐内单个员工退款。退款时：

- 订单状态改为 `REFUNDED`；
- 按订单快照金额计算退款；
- 套餐内所有订阅统一终止或恢复到购买前状态；
- 已使用的赠送算力不折现；
- 未使用的赠送算力标记为 `EXPIRED`，不转入企业钱包；
- 生成钱包退款流水或第三方退款记录；
- 写入审计日志。

如果现有退款实现暂时只支持单订阅，应先抽出“订单退款履约服务”，让员工订单和套餐订单都通过订单明细执行，避免在控制器中拼接退款逻辑。

## 9. 前端页面

### 9.1 平台运营端

在平台管理端增加“套餐管理”：

- 套餐列表：名称、编码、员工数量、售价、原价、状态、更新时间；
- 新建/编辑套餐：基本信息、员工选择、周期、价格；
- 发布前预览：员工原价合计、套餐售价、优惠金额、总赠送算力；
- 发布、下架、归档；
- 已发布套餐禁止直接修改影响订单的字段，编辑时采用新版本或先下架。

员工选择只能选择已审核上架的数字员工。选择员工后，前端展示该员工年费和按当前系统规则计算的预计赠送算力，最终金额仍以后端为准。

### 9.2 系统设置页

继续使用现有“系统设置 → 计费与额度”，增加/确认两个字段：

- 订阅赠送算力默认比例（%）；
- 订阅赠送算力固定默认值（元）。

不建议在套餐页面复制一份“全局默认比例”配置。套餐页面只展示计算结果，避免出现两处配置互相覆盖。

### 9.3 企业市场端

增加套餐列表和详情页：

- 套餐名称、说明和封面；
- 包含的员工；
- 员工原价合计；
- 套餐价格；
- 优惠金额；
- 总赠送算力；
- 购买按钮。

购买确认页要提示：

```text
购买后套餐内员工将立即加入企业订阅，赠送算力按员工分别到账。
套餐购买后第一版只支持整单退款，不支持单独退回其中一名员工。
```

### 9.4 订单和订阅展示

订单详情应显示：

- 订单类型：员工订阅 / 套餐购买；
- 套餐名称和套餐价格；
- 套餐内员工明细；
- 每个员工的订阅周期和赠送算力；
- 支付状态和履约状态。

订阅列表可以增加“来源”字段：直接订阅、套餐购买、管理员授权。

## 10. DTO 与校验

共享 DTO 使用现有 `shared` alias 和 Zod 校验，不把原始 `req.body` 传给 service。

建议 DTO：

```ts
const BundleItemDtoSchema = z.object({
  employeeId: z.string().min(1),
  periodMonths: z.number().int().min(1).max(36).default(12),
});

const CreateBundleDtoSchema = z.object({
  code: z.string().trim().min(1).max(64),
  name: z.string().trim().min(1).max(120),
  description: z.string().trim().max(5000).optional(),
  cover: z.string().trim().url().optional(),
  priceCNY: CnyAmountSchema,
  periodMonths: z.number().int().min(1).max(36).default(12),
  items: z.array(BundleItemDtoSchema).min(1).max(100),
});

const CreateBundleOrderDtoSchema = z.object({
  bundleId: z.string().min(1),
});
```

套餐项重复员工、无效价格、员工未上架、套餐未发布等错误使用 Nest HTTP exceptions，不抛原始 `Error`。

## 11. 测试计划

### 11.1 后端单元测试

必须覆盖：

- 默认比例为 10% 时正确计算赠送算力；
- 默认比例修改为 20% 后，新订单使用 20%；
- 已有员工固定金额时不受默认比例影响；
- 员工固定金额为 0 时确实不赠送；
- 比例为 0 时回退固定默认金额；
- 年费为空或为 0 时回退固定默认金额；
- 套餐不能包含重复员工；
- 套餐不能包含未审核员工；
- 套餐发布前必须有有效价格；
- 创建订单使用数据库中的套餐价格，忽略前端伪造价格；
- 创建订单固化套餐和员工快照；
- 已有 ACTIVE 订阅时拒绝下单；
- 套餐订单支付后创建全部订阅；
- 套餐订单履约失败时整单回滚；
- 重复支付通知不重复创建订阅和算力；
- 订单退款按成交快照计算；
- 赠送算力不会被退款为企业现金余额。

### 11.2 接口测试

覆盖：

- 平台管理员可以创建和发布套餐；
- 非平台管理员不能管理套餐；
- 市场访客可以查看已发布套餐；
- 草稿和归档套餐不会出现在市场；
- 企业管理员可以创建套餐订单；
- 普通成员不能创建购买订单；
- 跨企业订单详情访问返回 404；
- 订单支付回调重复调用保持幂等。

### 11.3 前端测试

- 系统设置页正确展示并提交默认比例；
- 员工固定算力为 0 时展示“不赠送”；
- 套餐详情展示员工清单、原价、套餐价和总赠送算力；
- 套餐支付失败时不显示已购买；
- 订单详情显示套餐明细；
- 套餐下架后购买按钮不可用。

## 14. 不在第一版实现的内容

- 企业购买后先进入员工库存，再分配给成员；
- 套餐内员工自由增删；
- 套餐共享算力池；
- 套餐内单个员工单独退款；
- 套餐自动续费；
- 套餐优惠券、阶梯价和渠道价；
- 多版本套餐同时销售；
- 套餐购买数量大于 1。

如果未来需要共享算力池，应新增独立的套餐算力批次账本，不能直接把赠送金额写入企业钱包 `totalDeposit`，也不能把共享额度伪装成某个员工的 `SubscriptionCredit`。

## 15. 验收标准

功能完成必须满足：

1. 运营人员可以在系统设置中修改默认赠送比例，默认值为 10%。
2. 员工级固定赠送金额可以覆盖系统默认比例，固定值为 0 时不赠送。
3. 运营人员可以创建、发布和下架固定套餐。
4. 企业管理员可以购买已发布套餐，普通成员不能购买。
5. 套餐订单价格由后端读取，前端不能篡改。
6. 支付成功后，套餐内所有员工在同一事务内完成订阅和授权。
7. 每个员工的赠送算力分别进入对应的 `SubscriptionCredit`。
8. 默认比例或员工配置变更不影响已支付订单和已有订阅。
9. 支付回调重复执行不会重复创建订阅或重复发放算力。
10. 订单、订阅、算力、退款和审计记录可以通过订单号关联追溯。
