# 员工换绑技能后 SEP 仍获取旧技能包：排查与修复方案

日期：2026-11-05
范围：SEP 后台、后端运行时接口、SEP Electron 客户端。本文是代码调查与开发方案，不包含生产写入。

## 结论摘要

这是两个可能同时出现、但需要分别处理的问题：

1. **运行时可能仍解析到旧技能**：任务按 `subscription.employeeId` 找员工绑定；同名员工是不同记录。即使绑定在正确员工上，运行时版本优先级仍是企业默认版本、订阅选版、员工绑定默认版本、平台回退版本。仅改员工模板绑定不保证订阅使用新技能/新版本。
2. **客户端会拒绝超限包的 manifest**：后端当前允许 `100 MiB / 10,000` 个包条目，SEP 客户端只接受 `20 MiB / 500` 个文件。后端可能返回 `AVAILABLE`，客户端在解析 manifest 时将整个响应判为无效，抛出 `Invalid employee runtime manifest.`。对 821 个文件的包，仅 `runtime.skills[i].artifact.fileCount` 超限就足以触发；若 `byteLength > 20 MiB`，`runtime.skills[i].artifact.byteLength` 也会超限。

**目前不能确认该订阅此刻实际选中的员工、技能版本和包字节数。** 生产库当前连接不可用，先前查询结论不能当作当前状态。下文的 SQL 和接口检查只读必要元数据，不选择 `systemPrompt`、技能正文或凭据。

## 代码路径与已证实行为

### 后台能力绑定

平台后台员工编辑页从 URL `params.id` 取得 `employeeId`，以该 ID 读取员工和绑定，并把同一个 ID 与 `capabilityIds` 发送到绑定 mutation：

- `web/src/app/(platform)/admin/employees/[id]/edit/page.tsx`：35、60-65、150-159 行。
- `web/src/features/admin/admin-api.ts`：483-494 行，调用 `POST /admin/employees/:id/bindings`。
- `backend/src/modules/admin/admin.controller.ts`：515-526 行，从路由参数取得 `employeeId` 并传给 service。
- `backend/src/modules/admin/admin.service.ts`：735-778 行，按该 `employeeId` 删除并重建能力绑定；每条绑定的 `defaultSkillVersionId` 取最新已审核平台版。

这条代码路径使用 ID 而不是员工名称，也没有发现把名称解析为员工的逻辑。React Query 的绑定查询键含 `employeeId`，成功后也按该 ID 失效缓存（`web/src/features/admin/use-admin.ts`：503-525 行）。因此，仅凭“后台显示名称相同”不能证明改到了订阅所指的记录；应核对员工 ID。后台当前调用绑定接口时会**整组替换该员工的能力绑定**，不是只追加一项。

企业员工详情的版本展示是另一条路径：`web/src/app/(enterprise)/my-employees/[id]/page.tsx` 调用 `GET /enterprise/employees/:employeeId/skills`。企业在能力版本时间线点“启用”则调用 `POST /enterprise/capabilities/:capabilityId/default-version`，见 `web/src/features/capability-iteration/use-capability-iteration.ts`：217-225 行及 `backend/src/modules/skill-version/skill-version.controller.ts`：229-241 行。它设置企业共享默认版本，不是修改员工绑定的 `defaultSkillVersionId`。

### 版本解析与传播

`SkillVersionService.resolveEffectiveVersion()`（`backend/src/modules/skill-version/skill-version.service.ts`：344-377 行）按以下顺序取第一个有效且已审核版本：

1. `EnterpriseSkillDefault` 企业默认
2. `SubscriptionSkillVersion` 订阅选版
3. 当前订阅员工的 `EmployeeCapabilityBinding.defaultSkillVersionId`
4. 已审核平台版本回退

有效性还要求版本 `capabilityId` 匹配；企业版必须属于当前企业且通过企业审核，平台版必须通过平台审核。

企业默认写入由 `EnterpriseSkillDefaultService.set()` 完成（`backend/src/modules/skill-version/enterprise-skill-default.service.ts`：16-65 行）。它会更新企业默认，并把相同版本写到当前所有有该能力绑定的有效订阅选版。因此，“员工绑定默认版是新版本”与“运行时最终用新版本”不是同一件事；企业默认是最高优先级。

### 运行时接口与客户端校验

`GET /api/client/subscriptions/:subscriptionId/runtime` 在 `backend/src/modules/client/client.controller.ts`：274-297 行，调用 `ClientService.getRuntime()`。

该 service：

- 先按订阅 ID、企业、有效期及成员/部门授权取订阅及其 `employee`（`client-subscription-access.ts`：5-17 行）。
- 从该订阅实际关联的员工读取启用且已审核的 SKILL 绑定；逐项调用 `resolveEffectiveVersion(subscription.id, capabilityId)`。
- 在 `skillArtifactProtocolVersion=1` 时附带 artifact 描述，返回技能 `capabilityId`、`versionId`、版本号、正文和 artifact 元数据（`backend/src/modules/client/client.service.ts`：747-795 行）。

客户端 `getEmployeeRuntime()` 请求 `?mediaProtocolVersion=3&skillArtifactProtocolVersion=1&videoProtocolVersion=3`，并在技能准备前调用 `parseEmployeeRuntimeManifest()`，见 `sep-client/electron/common/platform/platform-api.ts`：395-412 行和 `sep-client/electron/service/employee-authorizer.ts`：279-307 行。因此 schema 失败发生在技能下载/安装准备之前。

客户端限制定义在 `sep-client/electron/common/platform/skill-artifact-contract.ts`：4、46-61 行：`byteLength <= 20 MiB`、`fileCount <= 500`。manifest 的 artifact 位于 `runtime.skills[i].artifact`；字段约束失败路径为：

- `runtime.skills[i].artifact.fileCount`：821 > 500。
- `runtime.skills[i].artifact.byteLength`：若实际字节数大于 20 MiB，也会失败。当前没有生产元数据可确认实际字节数。

后端 `backend/src/shared/skill-content-schema.ts`：3-6 行将上传/安装包上限设为 100 MiB、10,000 entries；`client-skill-artifact.dto.ts`：37-50 行复用该限制。`ClientSkillArtifactService.prepare()` 用这个后端 schema 决定是否返回 `AVAILABLE`（`backend/src/modules/client/client-skill-artifact.service.ts`：55-84 行）。所以 821 个文件的 artifact 可被后端接受，但超过 SEP 客户端 schema。当前客户端 `parseEmployeeRuntimeManifest()` 抛出的错误是固定泛化文本，不带 Zod 的字段路径和值（`employee-runtime-contract.ts`：95-98 行）。

客户端 `EmployeeAuthorizer.readRuntime()` 每次授权都会调用 runtime provider；代码中有订阅目录 TTL 缓存，但 manifest 本身不从该目录缓存读取。当前证据不支持“旧 manifest 缓存”是这次 schema 错误的原因。

## 生产只读复核步骤

使用只读数据库会话，仅查询下列字段。不要 `SELECT *`，不要查询或打印 `digital_employees.systemPrompt`、`skill_versions.content`、配置 JSON、令牌或密钥。

```sql
BEGIN READ ONLY;

-- 1. 订阅当前指向哪个员工及企业。
SELECT s.id AS subscription_id, s."enterpriseId" AS enterprise_id,
       s."employeeId" AS employee_id, e.name AS employee_name,
       e.status AS employee_status, s.status AS subscription_status
FROM subscriptions s
JOIN digital_employees e ON e.id = s."employeeId"
WHERE s.id = 'cmw2vhusb038ztn019d8fbmue';

-- 2. 同名员工记录仅比较 ID/状态/更新时间，用于识别后台是否改了另一条记录。
SELECT id AS employee_id, name, status, "updatedAt" AS updated_at
FROM digital_employees
WHERE name = (
  SELECT e.name
  FROM subscriptions s JOIN digital_employees e ON e.id = s."employeeId"
  WHERE s.id = 'cmw2vhusb038ztn019d8fbmue'
)
ORDER BY "updatedAt" DESC, id;

-- 3. 订阅员工的能力绑定及绑定默认版；只返回包元数据，不读取正文。
SELECT b."employeeId" AS employee_id, e.name AS employee_name,
       b."capabilityId" AS capability_id, c.name AS capability_name,
       b.enabled, b."defaultSkillVersionId" AS binding_version_id,
       sv.version AS binding_version, sv.scope AS binding_scope,
       sv.status AS binding_version_status, sv."packageFileCount" AS package_file_count,
       sv."packageSha256" AS package_sha256
FROM employee_capability_bindings b
JOIN digital_employees e ON e.id = b."employeeId"
JOIN capabilities c ON c.id = b."capabilityId"
LEFT JOIN skill_versions sv ON sv.id = b."defaultSkillVersionId"
WHERE b."employeeId" = (
  SELECT "employeeId" FROM subscriptions WHERE id = 'cmw2vhusb038ztn019d8fbmue'
)
ORDER BY b.priority, c.name;

-- 4. 按上一步关注的 capabilityId 检查企业默认和该订阅的显式版本。
SELECT 'enterprise' AS source, d."capabilityId" AS capability_id,
       d."versionId" AS version_id, sv.version, sv.scope, sv.status
FROM enterprise_skill_defaults d
JOIN skill_versions sv ON sv.id = d."versionId"
WHERE d."enterpriseId" = (
  SELECT "enterpriseId" FROM subscriptions WHERE id = 'cmw2vhusb038ztn019d8fbmue'
)
AND d."capabilityId" = '<目标 capabilityId>'
UNION ALL
SELECT 'subscription' AS source, x."capabilityId" AS capability_id,
       x."versionId" AS version_id, sv.version, sv.scope, sv.status
FROM subscription_skill_versions x
JOIN skill_versions sv ON sv.id = x."versionId"
WHERE x."subscriptionId" = 'cmw2vhusb038ztn019d8fbmue'
AND x."capabilityId" = '<目标 capabilityId>';

ROLLBACK;
```

随后用该订阅的授权令牌请求 runtime 接口。不要加 `-v`、不要 `tee` 原始响应到文件，也不要打印原始 JSON。可在内存中只输出以下投影：

```js
const safe = {

  skills: (body.runtime?.skills ?? []).map(({ capabilityId, versionId, version, artifact }) => ({
    capabilityId, versionId, version,
    artifact: artifact && {
      status: artifact.status,
      ...(artifact.status === 'AVAILABLE' ? {
        byteLength: artifact.byteLength,
        fileCount: artifact.fileCount,
        format: artifact.format,
      } : { reason: artifact.reason }),
    },
  })),

console.log(JSON.stringify(safe, null, 2));
```

若通过 HTTP 客户端管道实现该投影，确认没有打印原始响应、请求头或令牌。用 `employee.id` 与数据库查出的订阅 `employeeId` 对照；用每项 `capabilityId/versionId` 对照四层选版数据；记录 artifact `status/byteLength/fileCount`。这一步才可确认当前生产的真实结果。

## 修复方案

### 当前订阅的最小数据修复

先完成上面的只读核对，再根据结果选择唯一正确动作，不要按名称直接改数据：

1. **订阅员工 ID 不符合预期**：由业务负责人确认应使用哪条员工记录。要么在订阅实际关联的员工 ID 上绑定目标能力，要么经授权调整订阅员工关联；不要因为同名就批量更新。改订阅关联会影响该订阅后续运行所用的员工模板，应单独评估。
2. **订阅员工缺目标 `capabilityId` 或仍留有旧能力**：在确认目标员工 ID 与能力 ID 后，更新正确员工的绑定集合。后台绑定 API 是整组替换；提交时应包含预期保留的全部能力。
3. **最终解析出的 `versionId` 仍为旧版**：按优先级核对 `enterprise_skill_defaults`、`subscription_skill_versions`、绑定默认值和平台回退。若目标版本对企业内所有使用该 capability 的订阅都应生效，使用现有企业“启用版本”功能把企业默认设为目标审核版；该操作会传播到匹配的有效订阅。若需求是只为单个员工/订阅选择不同版本，当前企业共享默认的写入路径不满足该隔离需求，需要先设计并实现明确的 per-subscription/per-employee 选版语义，不应直接假设后台按钮只改一条订阅。
4. **包超出客户端限制**：本问题的即时恢复优先选择已审核且包元数据符合客户端限制的版本（问题描述中的新包 42 个文件仍需实测 `byteLength`）。若必须保留旧版本，制作并审核一个在客户端限制内的新包版本；保留原包及版本记录，不覆盖或删除它们。
5. 只在运行时投影确认订阅员工、能力和目标 `versionId` 正确，且 artifact 为 `AVAILABLE`、大小/文件数在客户端上限内后，才重跑失败任务。

以上生产数据动作均需经负责人确认后另行执行；本次未执行。

### 已完成的本地代码修复

- 后端在返回 `AVAILABLE` 前应用客户端 `20 MiB / 500 files` 限制；超限时返回 `BLOCKED / CLIENT_LIMIT_EXCEEDED`，并提供有限的包大小/文件数元数据。通用上传/解包上限仍为 `100 MiB / 10,000`。
- Electron 客户端接受新的 blocked 元数据，并在授权阶段给出具体超限值；对旧服务端仍返回的超限 `AVAILABLE` manifest，会报告 `runtime.skills[i].artifact.byteLength/fileCount` 路径，不回显技能正文。
- 后端 artifact/schema 测试 156 项、客户端相关测试 81 项通过；两端 TypeScript 检查通过。

该修复可以阻止不兼容包进入技能安装并给出可读原因，但不会自动改变生产订阅员工或生效版本。生产数据仍须先只读核实，再按审批执行最小修正。

### 尚待评估的代码改进

1. **后台区分员工记录与实际生效版本**：在员工绑定编辑/详情中显示稳定员工 ID；企业订阅详情显示订阅实际 `employeeId`、目标能力 `capabilityId` 和解析后的有效版本来源/ID。用户查看“员工绑定默认版”时明确标注它可能被企业默认或订阅选版覆盖。
2. **保持数据诊断最小化**：运行时排障日志记录 `taskId`、`subscriptionId`、`employeeId`、`capabilityId`、`versionId`、artifact 状态/大小/文件数和 schema issue path；不记录技能正文、系统提示词或凭据。

其余可选改进涉及以下文件：

- `web/src/app/(platform)/admin/employees/[id]/edit/page.tsx` 和/或企业员工详情、版本信息组件（仅为 ID/有效版本可见性改进）。
- 如增加安全运行时诊断日志，再改 `backend/src/modules/client/client.service.ts` 及对应测试。
- 如需 per-subscription 选版：再明确新增/调整企业/订阅 API、service、shared DTO 和 Prisma 写入逻辑；这是独立行为变更，不属于本次只读调查。

## 回归测试范围

- **后端 artifact 描述**（`client-skill-artifact.service.spec.ts`）：500/501 文件边界、20 MiB/20 MiB+1 字节边界；超限包返回稳定 `BLOCKED` reason，不返回不兼容的 `AVAILABLE`；正常包维持 `AVAILABLE`；上传/通用归档允许范围不被意外改小。
- **客户端 schema 与诊断**（`skill-artifact-contract.test.ts`、`employee-runtime-contract.test.ts`）：合法边界仍接受；超限时报告 `runtime.skills[i].artifact.fileCount` 或 `.byteLength`；错误中不包含构造的技能正文、`systemPrompt` 或任意秘密标记。
- **版本解析优先级**（`skill-version-selection.spec.ts`）：分别验证企业默认、订阅选版、员工绑定默认、平台回退；加入同名但不同 ID 的员工数据，确认 resolver 只使用 `subscription.employeeId` 对应记录。
- **后台绑定 API/UI**（`admin.service.spec.ts`、员工编辑页 spec）：请求路由员工 ID 原样到达 service；对同名员工只修改目标 ID；批量绑定会重建目标员工绑定并给目标 capability 写入批准的平台默认版；成功后只失效目标员工 ID 对应查询。
- **runtime 集成**（`client.service.spec.ts` 或 HTTP 测试）：固定订阅员工、能力、企业默认/订阅选版后，请求 negotiated runtime；断言返回正确 capability/version/artifact 元数据；测试不序列化正文到日志。
- **端到端客户端准入**：后端返回超限包时 client 收到可解析的 `BLOCKED` descriptor，并给出具体原因；不会再以泛化 manifest parse 错误拒绝整个订阅；改用新合规版本后允许正常准备技能。

## 验收与发布顺序

1. 在只读生产会话核实订阅员工 ID、同名员工 ID、绑定 capability/version、企业默认和订阅选版。
2. 用 runtime 元数据投影核实实际 `employee.id`、`capabilityId/versionId`、artifact 状态、字节数和文件数；不保存或输出原始 manifest。
3. 在隔离环境完成后端及客户端契约测试和 runtime 集成测试；若两端限制/错误契约有变，后端与客户端按兼容顺序一起发布。
4. 获批后执行最小的订阅/版本数据修正；再次读取 runtime 元数据确认目标版本。
5. 以失败任务订阅重新授权/重试，确认旧包不再进入 runtime，且没有 `Invalid employee runtime manifest.`。
