# SEP 完整迁移部署手册

编写日期：2026-11-03。来源：仓库部署配置、应用实现及两台服务器的只读核查。

本文是迁移执行手册，不是迁移完成记录。编写时没有导出业务数据、停止应用、修改 DNS 或在新机启动服务。文中的停写、恢复、域名切换命令，只能在约定的迁移窗口按门禁执行。

2026-11-03 已执行服务器迁移，实际结果、备份位置、DNS 过渡方式及回退边界见 [迁移部署执行记录](2026-11-03-SEP迁移部署执行记录.md)。实际运行配置见 [独立服务器部署配置](../../deploy/standalone/README.md)。以下保留迁移前的方案与核查快照，不代表当前运行状态。

## 1. 目标与范围

把旧服务器上的 SEP 网站、生产数据库、用户文件、员工包、知识库原件、认证与业务配置迁到新服务器。先保持原域名和生产版本，再安排后续功能升级。

| 项目 | 旧环境 | 新环境 |
| --- | --- | --- |
| 公网 IP | `64.83.39.223` | `121.37.128.126` |
| SSH | `root`，Mac 别名 `longdao` | `root`，已验证密钥登录 |
| Mac 到新机的私钥 | 不适用 | `/Users/yao/.ssh/sep_deploy` |
| 新机到旧机的私钥 | 不适用 | `/root/.ssh/sep-migration-old`，已验证连接 |
| 操作系统 | 本次未核查 | Ubuntu 24.04.4 LTS，x86_64 |
| 新机资源 | 不适用 | 8 核、约 30 GiB 内存 |
| 新机系统盘 | 不适用 | `/` 约 197 GiB，可用约 184 GiB |
| 新机数据盘 | 不适用 | `/dev/sdb1` 挂载 `/www`，约 984 GiB，可用约 933 GiB |
| 新机挂载持久化 | 不适用 | 已在 fstab 查到 `/www` 挂载项 |
| 新机 Docker / Compose | 不适用 | 29.9.2 / v5.6.1；Docker 运行中，尚无容器 |
| 生产域名 | `longdaosep.cn`，配置中也有大小写变体 | 默认沿用；切换前核查 DNS、证书与回调 |

新服务器只迁 SEP。旧机的 sub2api、其数据库、共享 Redis DB 0、联调环境及其他站点继续留在旧机。若还要迁模型中转，应另立迁移计划，不能与 SEP 数据混在一起操作。

推荐访问结构：

```text
longdaosep.cn -> 新机 Caddy -> SEP Web -> SEP Backend
                          \-> /ws/* -> SEP Backend
                                         |-> 新机 PostgreSQL / sep_prod
                                         |-> 新机 Redis / DB 1
                                         |-> 现有 sub2api 的 HTTPS 地址
                                         \-> 独立 Ollama（恢复语义能力时部署）
```

### 必须保留的数据

| 数据 | 迁移方式 | 说明 |
| --- | --- | --- |
| `sep_prod` 全库 | `pg_dump -Fc` / `pg_restore` | 包括用户、会话、聊天、钱包、账单、任务、知识库向量、系统配置、Prisma 历史 |
| uploads | 卷内容 tar | 包括聊天附件、头像、媒体视频缓存等，保留整个 `/app/uploads` |
| packages | 卷内容 tar | 保留 `/app/storage/packages`，即使当前为空也建立挂载 |
| knowledge | 宿主目录 tar | 保留容器内 `/app/private/knowledge`；不得公开为静态目录 |
| tokenizers | 宿主目录 tar | 保留固定版本、摘要与容器内路径，只读挂载 |
| 生效配置与密钥 | 加密 SSH 传输到新机私有文件 | 不写进 Git、日志、聊天或本文 |
| 精确生产镜像 | `docker image save` / `load` | 首次迁移复用原镜像，避免同时引入代码与依赖升级 |
| 对应代码 | 固定 commit 的 `git archive` | 保留源码与排障依据，不用本地未发布代码替代生产代码 |

数据库里的部分密文通过 `JWT_SECRET` 派生密钥解密，不能随意重新生成它；`ACCESS_JWT_SECRET`、`REFRESH_TOKEN_PEPPER` 也必须保留，否则认证连续性会受影响。刷新会话主要保存在 PostgreSQL，不能简单认为清空 Redis 就一定全部退出登录。

## 3. 执行门禁与未确认项

迁移前完成以下核对，并记录执行人、计划窗口、实际耗时和每一步结果：

- [ ] 确认迁移范围为生产 SEP，旧机 sub2api 和联调继续运行。
- [ ] 确认沿用域名、A/AAAA/CNAME/CDN/负载均衡实际入口；不能只检查一条 A 记录。
- [ ] 确认现有证书的域名、有效期及 SEP 专属证书的安全导出方式。
- [ ] 确认新 IP 的华为云安全组放行 80/443；SSH 来源范围按运维需要设置。宿主机未监听不等于云安全组已放行。
- [ ] 确认面板/Nginx/Apache 没有占用 80/443；若选 Caddy，只让它管理 SEP 入口。
- [ ] 确认 sub2api HTTPS 地址可从新机访问；核查数据库设置中的容器地址、旧 IP、代理地址覆盖。
- [ ] 核查 SMTP、支付/回调、OAuth、OSS/对象存储、IP 白名单及客户端自定义 API 地址。
- [ ] 确认活动 commit、镜像 ID、所有文件挂载与任务状态，冻结自动部署。
- [ ] 完成一次隔离恢复演练，再约定正式停写窗口。
- [ ] 确认切换后的回滚规则，尤其是新机已经产生业务写入时的数据处理。

当前 Ollama 不可用是已知旧站缺口。迁移时可以保留相同状态并单独标记知识库语义能力未验收；若要求完整知识库能力上线，则必须先部署并验收 Ollama，不能以 Web 健康检查通过代替。

### 5.1 独立 Compose 参考

将以下内容保存为新机 `/www/sep/deploy/compose.yaml`。这是首次迁移的单套应用方案；没有直接复用旧站蓝绿发布脚本。镜像名称按第 2 节快照填写，正式执行时以重新核实的值为准。

旧 Web 镜像在构建时已经写入 `http://sep-green-backend:3001`，因此保留这个容器名。只修改 Web 的运行时 `API_ORIGIN` 不足以更改已构建 rewrite。

```yaml
name: sep-migration

x-logging: &logging
  driver: json-file
  options:
    max-size: "20m"
    max-file: "5"

services:
  postgres:
    image: longdao-postgres-pgvector:18.4-v0.8.1-9a8afca54e78
    container_name: sep-postgres
    restart: unless-stopped
    environment:
      POSTGRES_USER: sep_admin
      POSTGRES_PASSWORD: ${SEP_POSTGRES_ADMIN_PASSWORD:?required}
      POSTGRES_DB: postgres
      PGDATA: /var/lib/postgresql/data
      SEP_DB_PASSWORD: ${SEP_DB_PASSWORD:?required}
    volumes:
      - /www/sep/postgres:/var/lib/postgresql/data
    networks:
      sep:
        aliases: [longdao-postgres]
    healthcheck:
      test: [CMD-SHELL, "pg_isready -U sep_admin -d postgres"]
      interval: 10s
      timeout: 5s
      retries: 10
    logging: *logging

  redis:
    image: redis:8-alpine
    container_name: sep-redis
    restart: unless-stopped
    command: [redis-server, --appendonly, "yes"]
    volumes:
      - /www/sep/redis:/data
    networks:
      sep:
        aliases: [longdao-redis]
    healthcheck:
      test: [CMD, redis-cli, ping]
      interval: 10s
      timeout: 5s
      retries: 10
    logging: *logging

  backend:
    image: sep-green-backend:42fc2644a38b
    container_name: sep-green-backend
    restart: unless-stopped
    env_file:
      - path: ./backend.env
        format: raw
    environment:
      DATABASE_URL: ${SEP_DATABASE_URL:?required}
      REDIS_URL: redis://longdao-redis:6379/1
    volumes:
      - /www/sep/uploads:/app/uploads
      - /www/sep/packages:/app/storage/packages
      - /www/sep/knowledge:/app/private/knowledge
      - /www/sep/tokenizers:/app/tokenizers:ro
    networks: [sep]
    depends_on:
      postgres:
        condition: service_healthy
      redis:
        condition: service_healthy
    healthcheck:
      test: [CMD, node, -e, "fetch('http://127.0.0.1:3001/health').then(r=>process.exit(r.ok?0:1)).catch(()=>process.exit(1))"]
      interval: 10s
      timeout: 5s
      retries: 10
    logging: *logging

  web:
    image: sep-green-web:42fc2644a38b
    container_name: sep-green-web
    restart: unless-stopped
    environment:
      NODE_ENV: production
      API_ORIGIN: http://sep-green-backend:3001
      TZ: Asia/Shanghai
    networks: [sep]
    depends_on:
      backend:
        condition: service_healthy
    healthcheck:
      test: [CMD-SHELL, "wget -q -O /dev/null http://127.0.0.1:3000/"]
      interval: 10s
      timeout: 5s
      retries: 10
    logging: *logging

  migrator:
    image: sep-migrator:42fc2644a38b
    profiles: [tools]
    restart: "no"
    env_file:
      - path: ./backend.env
        format: raw
    environment:
      DATABASE_URL: ${SEP_DATABASE_URL:?required}
    networks: [sep]

  caddy:
    image: caddy:2-alpine
    container_name: sep-caddy
    profiles: [edge]
    restart: unless-stopped
    ports:
      - "80:80"
      - "443:443"
      - "443:443/udp"
    volumes:
      - ./Caddyfile:/etc/caddy/Caddyfile:ro
      - /www/sep/caddy/tls:/etc/caddy/tls:ro
      - /www/sep/caddy/data:/data
      - /www/sep/caddy/config:/config
      - /www/sep/caddy/logs:/var/log/caddy
    networks: [sep]
    logging: *logging

networks:
  sep:
    name: sep-migration-net
```

注意：这里故意不开放 5432、6379、3000、3001、11434 到公网。Redis 沿用旧环境无 AUTH 的内网连接方式，只接入 SEP 专属网络。不要把无关面板容器接入该网络。

这份配置使用 `env_file.format: raw` 保留 `$`、`#` 等密码字符；仅用于已经实测支持该功能的新机 Compose，不要拿旧版 Compose 直接启动。PostgreSQL 显式固定 PGDATA，以匹配本次复用镜像的既有目录结构，不依赖不同镜像版本的默认目录。

### 5.2 环境文件与辅助函数

新机 `/www/sep/deploy/.env` 至少包含：

```dotenv
SEP_POSTGRES_ADMIN_PASSWORD=<新机独立生成的管理员密码>
SEP_DB_PASSWORD=<新机SEP应用数据库密码>
SEP_DATABASE_URL=postgresql://sep_app:<经URL编码的应用数据库密码>@longdao-postgres:5432/sep_prod
```

管理员密码不要复用旧机共享数据库密码。应用库密码可以单独生成；若使用带特殊字符的密码，数据库 URL 中必须进行 URL 编码。环境文件中的 `$` 等还需按 Compose dotenv 规则引用；使用随机十六进制密码可减少编码问题。配置完成后 `chmod 600 /www/sep/deploy/.env`。

在新机定义 Compose 入口，后续 `dc` 均指这一份，避免误连旧站：

```bash
dc() {
  docker compose --env-file /www/sep/deploy/.env \
    -f /www/sep/deploy/compose.yaml "$@"
}
```

不要把 `docker compose config` 的完整输出贴到聊天或 CI 日志，它可能展开密钥；只用 `dc config -q` 检查配置。

## 6. 第一轮复制：源码、镜像与私有配置

先冻结生产自动发布或约定整个复制过程中不得发布，核实以下命令输出与第 2 节一致：

```bash
old 'git -C /opt/sep/app rev-parse HEAD'
old 'docker ps --format "{{.Names}} {{.Image}} {{.Status}}"'
old 'docker inspect sep-green-backend --format "{{range .Mounts}}{{printf \"%s %s %s\\n\" .Type .Source .Destination}}{{end}}"'
```

如果活动色已变，更新本文所有涉及的容器名、镜像标签和 Web 上游，不能仅替换一条命令。

建立这一轮迁移目录，记录目录名，后续不要误用上一轮备份：

```bash
SEP_MIGRATION_DIR="/www/sep/backups/migration-$(date -u +%Y%m%dT%H%M%SZ)"
install -d -m 700 "$SEP_MIGRATION_DIR"
printf '%s\n' "$SEP_MIGRATION_DIR"
SEP_PREPARED_DIR="$SEP_MIGRATION_DIR"
```

镜像直接从旧机流式拉取，不重新拉取同名浮动 tag：

```bash
old 'docker image inspect sep-green-backend:42fc2644a38b sep-green-web:42fc2644a38b sep-migrator:42fc2644a38b longdao-postgres-pgvector:18.4-v0.8.1-9a8afca54e78 redis:8-alpine caddy:2-alpine --format "{{.Id}}"' > "$SEP_MIGRATION_DIR/image-ids.txt"

old 'docker image save sep-green-backend:42fc2644a38b sep-green-web:42fc2644a38b sep-migrator:42fc2644a38b longdao-postgres-pgvector:18.4-v0.8.1-9a8afca54e78 redis:8-alpine caddy:2-alpine' \
  | gzip > "$SEP_MIGRATION_DIR/images.tar.gz.partial"
gzip -t "$SEP_MIGRATION_DIR/images.tar.gz.partial"
mv "$SEP_MIGRATION_DIR/images.tar.gz.partial" "$SEP_MIGRATION_DIR/images.tar.gz"
docker image load -i "$SEP_MIGRATION_DIR/images.tar.gz"

docker image inspect sep-green-backend:42fc2644a38b sep-green-web:42fc2644a38b sep-migrator:42fc2644a38b longdao-postgres-pgvector:18.4-v0.8.1-9a8afca54e78 redis:8-alpine caddy:2-alpine --format '{{.Id}}' > "$SEP_MIGRATION_DIR/loaded-image-ids.txt"
diff -u "$SEP_MIGRATION_DIR/image-ids.txt" "$SEP_MIGRATION_DIR/loaded-image-ids.txt"
```

记录旧站实际运行容器的 `.Image` 并与导出的 tag 对照，防止 tag 曾被重指向。上述 `diff` 必须无差异。首次迁移不把 PostgreSQL 18 的备份恢复到 16，也不把目录直接挂到其他大版本数据库。

源码与配置：

```bash
old 'git -C /opt/sep/app archive --format=tar 42fc2644a38b0e21566d28cd1f528f6e91321044' > "$SEP_MIGRATION_DIR/source.tar"
old 'git -C /opt/sep/app rev-parse HEAD' > "$SEP_MIGRATION_DIR/source-commit.txt"
old 'cat /opt/sep/.env' > "$SEP_MIGRATION_DIR/old-production.env"
old 'docker inspect sep-green-backend --format "{{json .Config.Env}}"' > "$SEP_MIGRATION_DIR/backend-runtime-env.json"
chmod 600 "$SEP_MIGRATION_DIR/old-production.env" "$SEP_MIGRATION_DIR/backend-runtime-env.json"
tar -xf "$SEP_MIGRATION_DIR/source.tar" -C /www/sep/source
```

重定向把秘密直接保存到新机文件，不能去掉 `>` 输出到终端，也不要启用 `set -x`。这些文件含生产凭据，不放入 Git。`git archive` 不包含 `.git`，将来启用 CI 前需要另行配置受控 Git checkout。

使用新机已有 `jq`（先 `command -v jq`，缺失时从 Ubuntu 官方仓库安装），检查运行时环境不存在换行后生成原始 env：

```bash
jq -e 'all(.[]; (contains("\n") | not) and (contains("\r") | not))' "$SEP_MIGRATION_DIR/backend-runtime-env.json" > /dev/null
jq -r '.[]' "$SEP_MIGRATION_DIR/backend-runtime-env.json" > /www/sep/deploy/backend.env
chmod 600 /www/sep/deploy/backend.env
```

若检查失败，单独处理多行密钥，不能继续生成损坏配置。原运行配置比 `.env.example` 更接近实际状态，但还需要人工审查并修改这些项：

- `DATABASE_URL`、`REDIS_URL` 由新 Compose 覆盖为新机服务。
- sub2api 使用可跨服务器访问的 HTTPS 地址；旧机的 Docker 容器名不能跨机解析。数据库 `system_settings` / 企业配置中的覆盖同样需要核查，不能只改 env。
- 保留认证、加密密钥和原域名、cookie 配置；保留 SMTP、媒体、OAuth 等生效配置。
- 容器内路径保持 `/app/uploads`、`/app/storage/packages`、`/app/private/knowledge`、`/app/tokenizers/...`；变化的是宿主路径。
- `TRUSTED_PROXY_CIDRS` 若已设置，按新代理链重新核实；不要复制宽泛信任网段。
- 检查模型默认值、预算、并发等运行配置。原蓝绿 Compose 与单套 Compose 透传项并不完全相同，不能重新生成时丢失生产参数。

## 7. 数据导出与传输

### 7.1 第一轮：演练用快照

在线 `pg_dump` 能得到数据库一致性快照，但在线复制文件和它不是同一个时间点。第一轮只用于恢复演练，不能直接作为正式停写后的最终数据。

在新机执行：

```bash
old 'docker exec longdao-postgres sh -c '\''exec pg_dump -U "$POSTGRES_USER" -d sep_prod --format=custom --no-owner --no-acl'\''' \
  > "$SEP_MIGRATION_DIR/sep.dump.partial"
test -s "$SEP_MIGRATION_DIR/sep.dump.partial"
mv "$SEP_MIGRATION_DIR/sep.dump.partial" "$SEP_MIGRATION_DIR/sep.dump"

old 'tar -C /var/lib/docker/volumes/sep_uploads/_data -cpf - .' > "$SEP_MIGRATION_DIR/uploads.tar.partial"
mv "$SEP_MIGRATION_DIR/uploads.tar.partial" "$SEP_MIGRATION_DIR/uploads.tar"
old 'tar -C /var/lib/docker/volumes/sep_packages/_data -cpf - .' > "$SEP_MIGRATION_DIR/packages.tar.partial"
mv "$SEP_MIGRATION_DIR/packages.tar.partial" "$SEP_MIGRATION_DIR/packages.tar"
old 'tar -C /opt/sep/knowledge -cpf - .' > "$SEP_MIGRATION_DIR/knowledge.tar.partial"
mv "$SEP_MIGRATION_DIR/knowledge.tar.partial" "$SEP_MIGRATION_DIR/knowledge.tar"
old 'tar -C /opt/sep/tokenizers -cpf - .' > "$SEP_MIGRATION_DIR/tokenizers.tar.partial"
mv "$SEP_MIGRATION_DIR/tokenizers.tar.partial" "$SEP_MIGRATION_DIR/tokenizers.tar"

docker run --rm --network none \
  -v "$SEP_MIGRATION_DIR:/backup:ro" \
  --entrypoint pg_restore longdao-postgres-pgvector:18.4-v0.8.1-9a8afca54e78 \
  --list /backup/sep.dump > "$SEP_MIGRATION_DIR/restore-list.txt"

(cd "$SEP_MIGRATION_DIR" && sha256sum sep.dump uploads.tar packages.tar knowledge.tar tokenizers.tar images.tar.gz source.tar > SHA256SUMS)
(cd "$SEP_MIGRATION_DIR" && sha256sum -c SHA256SUMS)
```

任一 SSH、tar、dump、哈希检查失败就停止。不要忽略 tar 的“文件在读取时变化”错误。可以在停写后重做；正式数据不接受不完整归档。哈希确认传输包之后没有变化，仍需恢复和业务对账验证语义完整性。

### 7.2 Redis 的处理

推荐：新机 Redis 冷启动，但先排空生产任务，检查数据库里的未完成任务并制定重入队方案。

Redis DB 1 包含 BullMQ `task-execution` 队列、临时验证码、会话锁、限流和媒体缓存，不能未经检查直接丢弃。长期认证会话在 PostgreSQL；临时验证码在切换后可能需要重新发送。

在旧机读取队列状态可以通过新机执行：

```bash
old 'docker exec longdao-redis sh -c '\''unset REDISCLI_AUTH; for k in wait active paused; do printf "%s=" "$k"; redis-cli -n 1 LLEN "bull:task-execution:$k"; done; for k in delayed prioritized waiting-children; do printf "%s=" "$k"; redis-cli -n 1 ZCARD "bull:task-execution:$k"; done'\'''
```

这些默认队列键还需与当前代码/运行前缀核对。正式切换门禁是待执行、活动、暂停、延时、优先、等待子任务均为 0，并核对 `task_runs`、`task_run_steps`、`knowledge_processing_jobs`、待结算账本等持久状态。任务数为零不代表所有模型账单已结算。

若有无法完成的任务，先记录任务 ID、数据库状态和允许的重试策略。不要盲目重跑支付、外部 RPA 或模型请求。需要保留队列时，单独制定 DB 1 选择性迁移与 TTL 保持方案。

禁止直接搬共享 Redis 的 RDB/AOF：它包含 sub2api 的 DB 0 和联调 DB 2。`redis-cli -n 1 --rdb` 也不能作为“只备份 DB 1”的方法；RDB 是实例级快照。

## 8. 隔离恢复演练与正式恢复

先演练，正式停写后再按同样步骤恢复最终包。演练时必须复制一份 Compose，整体替换目录为 `/www/sep-rehearsal`，使用独立项目名、网络名和所有容器名，并修正其 Web 上游；绝不能让演练访问生产数据库、Redis 或挂载生产目录。

演练优先只启动数据库，做数据恢复、表数和文件校验。若启动完整后端，它会运行 worker、定时任务和账单补偿；在隔离策略未落实前，不得接入生产 sub2api、SMTP、支付、RPA 回调或公网流量。完整演练需要独立测试凭据、固定新 Web 构建及受控外联，否则只做离线演练并把应用联调留到停写后。

以下 `dc`、`/www/sep/...` 命令是正式目标的恢复步骤；首次演练必须替换为演练目标，不能原样执行。

### 8.1 初始化空数据库

确认 `/www/sep/postgres` 是空的专用目标，目标还没有业务数据；已有数据时先备份并制定明确的替换步骤，不要执行 `--clean` 覆盖。

```bash
dc config -q
dc up -d postgres redis
dc ps
dc exec -T postgres pg_isready -U sep_admin -d postgres
dc exec -T redis redis-cli PING
dc exec -T postgres psql -X -v ON_ERROR_STOP=1 -U sep_admin -d postgres \
  -c "SELECT rolname, rolsuper FROM pg_roles WHERE rolname='sep_admin'" \
  -c "SELECT name, default_version FROM pg_available_extensions WHERE name IN ('vector','pg_trgm')"
```

门禁：`sep_admin` 必须是新机独立实例的管理员，且两项扩展都可用。`en_US.utf8` 是旧库实测值，本次复用同一个数据库镜像；若目标不能创建该 locale，应停止排查镜像/locale，不能随手改成其他排序规则继续恢复。

只在新目标首次初始化时运行：

```bash
dc exec -T postgres psql -X -v ON_ERROR_STOP=1 -U sep_admin -d postgres <<'SQL'
\getenv sep_password SEP_DB_PASSWORD
CREATE ROLE sep_app LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE PASSWORD :'sep_password';
CREATE ROLE sep_restore NOLOGIN SUPERUSER;
CREATE DATABASE sep_prod OWNER sep_app TEMPLATE template0 ENCODING 'UTF8' LC_COLLATE 'en_US.utf8' LC_CTYPE 'en_US.utf8' LOCALE_PROVIDER libc;
SQL
```

`sep_restore` 是新机本地的一次性恢复角色，用于恢复需要高权限创建的扩展；不开放登录，也不用于应用连接。应用继续使用低权 `sep_app`。

恢复前检查 `restore-list.txt` 中包含 `vector` / `pg_trgm` 的扩展条目。恢复时由 `sep_restore` 创建扩展，避免先用另一角色预建后再遇到扩展所有权错误；任何扩展缺失、权限失败或恢复报错都阻止应用启动。

### 8.2 恢复数据库和文件

```bash
(cd "$SEP_MIGRATION_DIR" && sha256sum -c SHA256SUMS)
dc exec -T postgres pg_restore \
  --username=sep_admin --dbname=sep_prod --role=sep_restore \
  --no-owner --no-acl --exit-on-error \
  < "$SEP_MIGRATION_DIR/sep.dump"

dc exec -T postgres psql -X -v ON_ERROR_STOP=1 -U sep_admin -d sep_prod <<'SQL'
REASSIGN OWNED BY sep_restore TO sep_app;
SQL
dc exec -T postgres psql -X -v ON_ERROR_STOP=1 -U sep_admin -d postgres -c 'DROP ROLE sep_restore;'

tar -xpf "$SEP_MIGRATION_DIR/uploads.tar" -C /www/sep/uploads
tar -xpf "$SEP_MIGRATION_DIR/packages.tar" -C /www/sep/packages
tar -xpf "$SEP_MIGRATION_DIR/knowledge.tar" -C /www/sep/knowledge
tar -xpf "$SEP_MIGRATION_DIR/tokenizers.tar" -C /www/sep/tokenizers
```

恢复失败时应用保持停止。不要在半恢复数据库上继续启动或反复覆盖导入，先保留日志并换新的空目标重新恢复。演练数据与正式数据分别使用全新目录和数据库，避免遗留演练文件或试验记录。

确认镜像中的 `node` UID/GID，再设置权限：

```bash
docker run --rm --network none --entrypoint id sep-green-backend:42fc2644a38b node
```

若输出为 UID/GID `1000:1000`，可以执行：

```bash
chown -R 1000:1000 /www/sep/uploads /www/sep/packages /www/sep/knowledge
chmod 700 /www/sep/uploads /www/sep/packages /www/sep/knowledge
chmod -R a+rX /www/sep/tokenizers
```

若 UID/GID 不同，替换为实测值。不要对全部 `/www` 递归改属主。知识库私有目录不挂到 Caddy，上传目录的公开访问继续经应用原有权限和路由。

### 8.3 数据库与文件核验

使用目标数据库执行项目提供的只读向量结构检查：

```bash
dc exec -T postgres psql -X -v ON_ERROR_STOP=1 -U sep_admin -d sep_prod \
  < /www/sep/source/deploy/production/postgres/verify-knowledge-schema.sql
```

对旧库与新库执行相同查询并比对，正式对账时旧站必须已停写：

```sql
SELECT extname, extversion FROM pg_extension ORDER BY extname;
SELECT count(*) AS users FROM users;
SELECT count(*) AS enterprises FROM enterprises;
SELECT count(*) AS sessions FROM auth_sessions;
SELECT count(*) AS conversations FROM conversation_sessions;
SELECT count(*) AS messages FROM messages;
SELECT count(*) AS subscriptions FROM subscriptions;
SELECT count(*) AS tasks FROM task_runs;
SELECT count(*) AS chunks FROM text_chunks;
SELECT count(*) AS documents FROM documents;
SELECT count(*) AS packages FROM employee_packages;
SELECT count(*) AS migrations FROM _prisma_migrations

```

另对企业/个人钱包余额、交易笔数与金额、待结算记录、付款订单、任务终态、文档与向量版本做业务对账；验收记录只存放在受限目录，不公开明细。行数一致只能发现部分错误，不能替代金额和引用关系核验。

为每个源文件目录生成按相对路径排序的 `sha256sum` 清单，在目标目录生成同样清单后比较，并核查目录结构、符号链接、权限及数据库中的文件引用。归档包校验之外，还应抽样打开旧附件、头像、员工包和知识原件。

例如正式停写后，对 uploads 执行以下内容级检查；packages、knowledge、tokenizers 按同样方式替换路径：

```bash
old 'cd /var/lib/docker/volumes/sep_uploads/_data && find . -type f -print0 | LC_ALL=C sort -z | xargs -0 -r sha256sum' > "$SEP_MIGRATION_DIR/uploads-files.sha256"
(cd /www/sep/uploads && sha256sum -c "$SEP_MIGRATION_DIR/uploads-files.sha256")

diff -u "$SEP_MIGRATION_DIR/uploads-files.sha256" "$SEP_MIGRATION_DIR/uploads-target.sha256"
```

这样既检查源文件内容，又发现目标里多出的文件。以上清单包含文件路径，按私有备份保护。源目录如果变化，检查结果也必须重做，不能混用演练清单。

首次迁移使用原代码和原库历史，不强行补跑本地较新的 migration，也不执行 `prisma migrate dev`、`db:reset`、全量 seed。若原镜像确有待部署迁移，先在演练库确认，再用匹配版本 migrator 的 `prisma migrate deploy`；迁移文件不能手改或删记录绕过。

在新 worker 启动前，用同一发布版本的 migrator 检查迁移账本：

```bash
dc --profile tools run --rm migrator pnpm --filter backend exec prisma migrate status
```

其结果应与固定源码/镜像对应，且没有失败或待处理迁移。若有差异先查清原因；经过演练确认确需补齐时，才执行 `dc --profile tools run --rm migrator`（该镜像默认命令为 `prisma migrate deploy`），然后重做结构检查和对账。

## 9. HTTPS 与应用启动

### 9.1 提前准备 HTTPS

正式域名仍指向旧机时，新机不能指望普通 HTTP-01 自动签发成功。选择其中一种：

1. 安全导出仅属于 SEP 域名的现有有效证书与私钥，传到新机 `/www/sep/caddy/tls/sep.crt`、`sep.key`，私钥权限 600。
2. 使用 DNS-01 提前签发。核实当前 Caddy 构建是否含 DNS provider 模块；没有模块时用受控证书工具签发，再挂载给 Caddy。
3. 明确接受切流时签证书的不可用窗口；证书未就绪前不宣布迁移完成。

不能复制旧机整个 Caddy 数据卷，它还包含其他域名的私钥。证书传输使用 SSH/SCP 重定向，不把私钥打印到日志。不要用关闭 TLS 校验来通过验收。

在 `/www/sep/deploy/Caddyfile` 使用正式域名；以下示例采用预先准备的 SEP 证书：

```caddyfile
longdaosep.cn {
    tls /etc/caddy/tls/sep.crt /etc/caddy/tls/sep.key

    @sep_ws path /ws/*
    reverse_proxy @sep_ws sep-green-backend:3001 {
        header_up X-Real-IP {remote_host}
        header_up X-Forwarded-For {remote_host}
        header_up X-Forwarded-Proto {scheme}
    }
    reverse_proxy sep-green-web:3000 {
        flush_interval -1
        header_up X-Real-IP {remote_host}
        header_up X-Forwarded-For {remote_host}
        header_up X-Forwarded-Proto {scheme}
        header_up X-Forwarded-Host {host}
    }
    log {
        output file /var/log/caddy/sep.log {
            roll_size 50mb
            roll_keep 5
        }
    }
}
```

HTTP API 经 Next.js rewrite 转发，WebSocket 直接到后端，两条链路都需验证。初始入口可先用维护响应；正式应用尚未验收时，不把 80/443 开放给普通业务写入。

上述 Caddyfile 的三种证书来源都必须最终提供这两个文件；若改由 Caddy 自动签发/续期，需要同时调整 `tls` 配置和 provider，不能保留静态文件配置却不提供文件。首次验收前检查 `test -s /www/sep/caddy/tls/sep.crt` 与 `test -s /www/sep/caddy/tls/sep.key`；静态证书不由 Caddy 自动续期，上线交接必须安排续期、到期告警和 reload。

### 9.2 启动与探测

正式启动前必须先完成第 10 节的旧站停写和最终恢复；在线演练不能启动会操作真实生产外部服务的同库副本。

```bash
dc config -q
dc up -d backend web
dc ps
dc exec -T backend node -e "fetch('http://127.0.0.1:3001/health').then(async r=>{console.log(r.status);console.log(await r.text());process.exit(r.ok?0:1)}).catch(()=>process.exit(1))"
dc exec -T backend node -e "fetch('http://127.0.0.1:3001/api/health/ready').then(async r=>{console.log(r.status);console.log(await r.text());process.exit(r.ok?0:1)}).catch(()=>process.exit(1))"
dc exec -T backend node -e "const fs=require('fs');for(const d of ['/app/uploads','/app/storage/packages','/app/private/knowledge']){const f=d+'/.migration-write-'+process.pid;fs.writeFileSync(f,'ok',{flag:'wx'});fs.unlinkSync(f);console.log(d+' writable')}"

dc --profile edge run --rm --no-deps caddy caddy validate --config /etc/caddy/Caddyfile
dc --profile edge up -d caddy
curl --resolve longdaosep.cn:443:121.37.128.126 -I https://longdaosep.cn/
```

`/health` 只代表存活；`/api/health/ready` 才是核心服务就绪门禁，但它不验证 embedding。检查日志时避免泄露请求、密钥或用户数据。

浏览器联调可在测试 Mac 的 hosts 临时把域名指向新 IP，保留原域名、HTTPS、cookie 与 WebSocket 行为；验收后撤销本机 hosts。`curl --resolve` 不改变公共 DNS，也不会绕过证书校验。

## 10. 正式停写与切换顺序

这一节是正式执行顺序。前面数据恢复章节是操作参考，不代表要提前把演练数据当成生产启动。

1. **准备窗口**：停止自动发布；降低权威 DNS TTL（例如 300 秒），至少提前等待原 TTL 过去。冻结新任务提交，提前把队列和知识处理任务处理完，记录仍需补偿的账单。对现有连接和最长模型请求预留排空时间。
2. **旧站进入维护**：只替换旧 Caddy 的 SEP 站点块为维护响应，备份并 validate/reload；不改模型中转域名和其他站点。入口维护应挡住页面、API、WebSocket、客户端及回调写入；同时阻断能绕过入口的直连调用。支付回调需核实上游重试/补查方案，不能丢单。
3. **停止生产写入者**：在旧机 `/opt/sep/app/deploy/production` 执行 `./sep-deploy.sh stop`。确认活动后端与 Web 已停止、任务完成、账单状态已记录。停止后再次查询队列以及 `task_runs`、`task_run_steps`、`knowledge_processing_jobs` 的状态分布；任何非终态记录都必须有明确的恢复/重入队决定，才能启动新 worker。检查是否还有直连数据库的脚本/worker。不要停止共享 PostgreSQL、Redis、Caddy、sub2api 或联调容器。排空超时则保留现场，不能用 SIGKILL 硬切。
4. **最终备份**：在新机新建一个带时间戳的 `SEP_MIGRATION_DIR`，保留演练包。按第 7 节重新导出 `sep_prod` 和四类文件；重新保存生产配置、commit、镜像 ID 和停写后的对账结果。旧机继续维护，不再恢复写入。
5. **正式恢复**：确认新生产目标为空，在新机执行第 8 节恢复最终包、权限检查、结构和金额/文件对账；失败就停止，旧站仍保留原数据。
6. **受控启动新站**：按第 9 节启动并通过固定域名定向验证。测试人员可以产生限定测试写入；在此之后回滚需按第 12 节处理新写入，不能再简单切回旧库。
7. **切换 DNS/上游**：把 SEP 的 A 记录改到 `121.37.128.126`；处理残留 AAAA、CDN/WAF/负载均衡源站。sub2api 域名继续指向其原服务。检查不同解析器和公网实际入口。
8. **处理 DNS 缓存期**：旧 SEP 入口保持维护，或作为仅转发 SEP 到新站的临时代理；绝不同时启用旧后端写旧库。临时代理必须明确新源站，避免按原域名解析回自身形成循环，并验证 TLS/SNI 与真实来源头。
9. **观察与交接**：按第 11 节验收，观察错误、回调、任务和账单。建议保留旧站应用、镜像和备份至少 7 天；旧机 sub2api/联调仍依赖共享设施，不能整机下线。

步骤 4 切换最终目录时，可复用已经核验的只读镜像与源码归档，其他数据必须重新导出：

```bash
test -n "${SEP_PREPARED_DIR:-}"
SEP_MIGRATION_DIR="/www/sep/backups/final-$(date -u +%Y%m%dT%H%M%SZ)"
install -d -m 700 "$SEP_MIGRATION_DIR"
cp --reflink=auto "$SEP_PREPARED_DIR/images.tar.gz" "$SEP_MIGRATION_DIR/images.tar.gz"
cp --reflink=auto "$SEP_PREPARED_DIR/source.tar" "$SEP_MIGRATION_DIR/source.tar"
cp "$SEP_PREPARED_DIR/image-ids.txt" "$SEP_MIGRATION_DIR/image-ids.txt"
cp "$SEP_PREPARED_DIR/source-commit.txt" "$SEP_MIGRATION_DIR/source-commit.txt"
old 'cat /opt/sep/.env' > "$SEP_MIGRATION_DIR/old-production.env"
old 'docker inspect sep-green-backend --format "{{json .Config.Env}}"' > "$SEP_MIGRATION_DIR/backend-runtime-env.json"
```

以上复用的前提是冻结期间版本与镜像 ID 未变；发生发布则重新准备镜像和源码。随后重跑第 7.1 节生成最终 dump、文件归档和 SHA256SUMS，并保存第 8.3 节停写基线。若配置与准备阶段不同，重新审查新机 backend.env；不要在新机生效配置里恢复旧数据库地址。

停机时间主要来自最终备份、恢复、对账和受控验收。当前 SEP 库和文件较小，但镜像、网络、向量索引和外部服务可能影响耗时，以演练计时为准，不提前承诺零停机。

## 11. 上线验收与知识库恢复

| 验收项 | 通过标准 |
| --- | --- |
| 入口 | 正式域名证书有效，HTTP 跳 HTTPS，80/443 外部可达，旧入口不写旧库 |
| 核心健康 | 后端 liveness、readiness 和 Web 全部通过 |
| 用户与认证 | 旧账号登录、页面刷新、refresh cookie、退出与重新登录正常 |
| 数据一致 | 停写基线的关键表、钱包余额、账本、订单、任务与文件引用一致 |
| 文件 | 旧头像/附件/视频/员工包可读取，新文件可写，私有原件不能匿名获取 |
| 对话和模型 | sub2api 地址正确，对话/SSE/停止生成可用，不能只看首页 |
| 任务 | 新任务入队、worker 执行、事件流与最终状态正常，不重复执行旧任务 |
| 媒体 | 已启用图片/视频链路和历史产物读取正常；真实调用按测试预算执行 |
| 邮件/OAuth | 受控测试邮箱可收验证码/找回邮件，已启用登录回调正确 |
| 支付 | 历史订单、钱包、回调重试和对账通过；真实付款测试另行安排 |
| 运维 | 数据盘挂载、容器重启策略、日志轮转、备份与告警有效 |
| 客户端 | 自定义 API 地址、WebSocket、回调或旧 IP 直连配置已更新 |

知识库语义能力是单独门禁：

1. 先核实是否还有独立 Ollama 主机或旧宿主机模型目录；当前没有可直接迁的 Docker 模型卷，不能假设模型已复制。
2. 按 [Embedding 服务部署指南](embedding-service.md) 部署独立 Ollama；模型放 `/www/sep/ollama`，只接入 SEP 内网，不公开 11434。
3. 固定模型 manifest、发布别名和 tokenizer，不能拉 `latest` 后直接宣称兼容。当前基线为 `bge-m3:sep-790764642607`、1024 维。
4. 同时核查 env 与数据库设置中的 embedding URL，确保新后端能访问 `sep-ollama`。
5. 验证 `/api/tags` 摘要、原生 `/api/embed` 输出、已有知识检索、原件权限和新文档处理发布。
6. 没有替换模型/版本时不要重建全部向量；若需换模型，按现有版本作业重建并单独验收。

若暂不恢复 Ollama，交接记录明确写“核心平台迁移完成，知识库语义能力未恢复/未验收”。

## 12. 回滚规则

### 情况 A：新机尚未产生任何业务写入

保持新机对外维护，停止新后端的 worker/定时处理；确认没有新增账单、任务或用户操作，再恢复旧站原 SEP Caddy 配置和原应用准入，DNS 指回旧机。启动旧应用前检查排空标记、实例 boot 与实际 readiness。

旧站恢复使用匹配的旧部署脚本和保留容器；先核查 `./sep-deploy.sh restart` 的恢复行为，不直接删除 drain 标记或重建镜像。确认旧站就绪后开放入口，处理 DNS 缓存期的访问。

### 情况 B：新机已产生写入或执行外部动作

不能仅把 DNS 改回去，否则新用户、消息、余额和订单会丢失或重复。正确流程是：

1. 新入口进入维护，排空并停止所有新写入者。
2. 备份新机数据库、文件、未完成任务和待结算状态，保存旧机基线。
3. 优先在新机修复；确需退回旧机时，先在旧机新的 SEP 专用目标恢复新机最终数据并验收，再让旧应用指向它。
4. 核对模型调用、支付、RPA 等外部动作，按幂等键和账本处理，不能靠数据库回滚撤销外部操作。
5. 保证任一时刻只有一套生产写入者，再切流量。

所有覆盖已有数据库或删除数据目录的步骤都需明确目标和备份，不能以自动“回滚”名义执行破坏性恢复。

## 13. 迁移后的发布、备份与清理

### 发布接管

当前仓库 `.github/workflows/{deploy,manual-deploy,full-deploy}.yml` 仍调用 `/opt/sep/app/deploy/production/sep-deploy.sh`。该脚本绑定旧机共享网络、Compose、状态目录和 Caddy 路径；本次独立 Compose 不能直接接管这些调用。

因此首次迁移不要仅把 GitHub `SERVER_HOST` 改成新 IP 就恢复自动部署。应先完成以下独立改造并测试，再启用 CI：

- 新机受控 Git checkout 与精确 commit 发布；不覆盖用户改动，不使用旧 Full Deploy 的强制清理流程。
- 新 Compose 的生产配置与迁移入口，后续是否继续成对蓝绿发布。
- Caddy 文件、容器名、网络、数据盘、排空/回滚与部署锁路径适配。
- 环境文件权限、备份与恢复演练、新版本 Prisma 迁移顺序。
- 再更新 GitHub host/user/port/key，测试手动发布后恢复自动触发。

### 备份

按业务恢复目标安排 PostgreSQL 和所有持久文件的定时备份，并保留版本、时间、校验和及密钥的安全恢复方式。迁移包在同一块 1 TB 盘上只是副本，不是异机备份；至少再保留一份到独立存储/对象存储，限制访问并做恢复抽查。

仓库现有 `backup-sep.sh` 默认只处理 `DATABASE_URL` 指向的库和 `/opt/sep/uploads`，不会自动发现实际 Docker uploads 卷、packages、私有 knowledge 和 tokenizer；`restore-sep.sh` 还使用覆盖式恢复。它们不能原样当成本次完整备份恢复工具。

### 重启与挂载

新机部署完成后，安排一次受控重启演练：核实 `/www` 先挂载，再恢复容器并验证 readiness、文件写入和外部访问。fstab 有记录不等于所有启动依赖已经正确；若数据盘缺失，Docker 不能在系统盘同名空目录中初始化一套新数据。

根据宝塔面板与 Docker 的实际管理方式，为容器启动配置数据盘挂载依赖（例如 Docker systemd 单元使用 `RequiresMountsFor=/www`，并核实挂载点），测试盘未就绪时应阻止业务启动。这一步影响宿主 Docker 生命周期，执行前需确认现有面板容器的依赖，不在迁移中途直接重启 Docker。

### 清理与凭据撤销

验收、观察期和异机备份完成后，撤销旧机 `authorized_keys` 中注释为 `sep-migration-12137` 的临时公钥，再安全处理新机对应临时私钥。不要动其他项目的密钥。

清理必须按明确目录、卷、镜像逐项核实，不执行全局 `docker system prune -a`、`compose down -v`，不删除旧机共享 PostgreSQL/Redis/Caddy。旧站回滚数据保留到约定期限后再处理。
