## 1. 结论先行

当前已知主机容量如下：

| 路径 | 容量/占用 | 现场证据 |
| --- | ---: | --- |
| 系统盘 `/` | 197G，总计；缓存清理后已用约 48G | 只读核查结果，2026-11-07 |
| 数据盘 `/www` | 984G，总计；迁移完成后已用约 88G | 服务器复核，2026-11-07 |
| SEP `/www/sep` | 约 40G | 只读核查结果 |
| 默认 Docker 数据目录 | `/www/sep/runtime/docker`，约 3.9G；旧 `/var/lib/docker` 约 123M | 迁移后复核，旧目录保留 |
| 默认 containerd 根目录 | `/www/sep/runtime/containerd`，约 43G；旧 `/var/lib/containerd` 约 43G | 迁移后复核，旧目录保留 |
| longdao Docker `/www/longdao/runtime/docker` | 约 1.3G | 清理后只读核查结果 |

**长期目标：服务器上 SEP、sub2api 及其后续容器部署的镜像、容器快照、Docker 元数据、构建缓存、容器日志和持久业务数据均放在数据盘 `/www`。**操作系统、系统软件包、systemd 配置和 `/run` 下的临时运行状态继续留在系统盘；不应把整个 `/var`、`/usr` 或根文件系统搬到数据盘。

建议系统默认 Docker 的两类持久目录都迁到 `/www` 的独立路径：containerd `root` 放在 `/www/sep/runtime/containerd`，Docker `data-root` 放在 `/www/sep/runtime/docker`。只有确认默认 Docker daemon 不承载 SEP 以外的服务后才采用项目目录前缀；若承载其他项目，则改用共享运行时专用路径（如 `/www/runtime/default-docker` 和 `/www/runtime/default-containerd`），并将所有依赖该 daemon 的部署统一纳入迁移和备份计划。longdao 独立 daemon 继续使用 `/www/longdao/runtime/docker` 和 `/www/longdao/runtime/containerd`，两套 daemon 绝不共享目录。

迁移执行前已核验服务归属、backend、挂载与回滚；43G 是目录占用快照，不代表其中每个文件都属于 Docker 镜像或可直接搬迁。迁移的是经核实的整个持久化根目录，不是手工挑选或删除 containerd 内部文件。

后续新服务按以下规则落盘：

- 服务配置与发布版本放 `/www/<project>/deploy`、`/www/<project>/releases`；密钥只保存在服务器受限配置文件或密钥管理系统，不进 Git。
- 数据库、上传和需要跨容器重建保留的数据放 `/www/<project>/data` 下的独立目录，并在 Compose 中显式 bind mount。
- 备份放 `/www/<project>/backups`，设置保留期限并定期验证可恢复性。
- 镜像、container snapshots、构建缓存及 Docker 容器日志属于 daemon 级存储，统一放到对应 Docker/containerd daemon 独占的 `/www/runtime/<daemon-name>/...`；不放进项目业务数据目录，也不让多个 daemon 共用。
- `/etc` 中的系统服务配置和 `/run` 临时状态留在系统盘。所有依赖数据盘路径的 systemd 服务都必须设置挂载依赖，防止 `/www` 未挂载时写入根盘空目录。

不要把 `/var/lib/docker` 改到 `/www/longdao/runtime/docker`，也不要让 SEP/系统 Docker 与 longdao Docker 共用任何 `data-root` 或 containerd `root`。Docker 官方明确要求不同 daemon 使用独立目录；共享目录会产生难以排查的错误。[Docker daemon 配置概览](https://docs.docker.com/engine/daemon/#configure-the-data-directory-location)

## 2. 关键存储边界

### 2.1 先确认实际 backend，再决定迁移对象

Docker 官方文档区分两种布局：

- 传统 storage driver（例如升级安装中常见的 `overlay2`）：镜像和容器数据都在 `/var/lib/docker`。
- containerd image store：镜像内容和 container snapshots 在 `/var/lib/containerd`，Docker 的卷、配置等其他 daemon 数据仍在 `/var/lib/docker`。[Docker daemon 配置概览](https://docs.docker.com/engine/daemon/#daemon-data-directory)

迁移窗口前必须记录以下只读结果：

```bash
docker info --format 'Driver={{.Driver}}\nDriverStatus={{json .DriverStatus}}\nDockerRootDir={{.DockerRootDir}}\nLoggingDriver={{.LoggingDriver}}'
docker system df -v
du -sh /var/lib/docker /var/lib/containerd
systemctl is-active docker containerd
systemctl cat docker.service containerd.service
```

如果 `DriverStatus` 显示 `io.containerd.snapshotter.v1`，并且通过 unit、socket、配置和服务进程确认 `/var/lib/containerd` 归该 Docker daemon 使用，才按 containerd image store 路径处理；如果显示 `overlay2` 或其他传统 driver，则不能把约 43G 的 `/var/lib/containerd` 直接当成 Docker 镜像层迁移对象。实际版本、backend、containerd 实例归属、是否存在第二个 Docker daemon，必须以现场结果为准，本文不替代核查。

### 2.2 `data-root` 不覆盖 containerd snapshots

这是本策略最重要的边界。Docker 官方明确写明：在使用 containerd image store 时，`data-root` **不会影响** `/var/lib/containerd` 中的镜像和 container 数据；要迁移 containerd snapshotters，需单独配置 `/etc/containerd/config.toml` 的 `root`。[Docker daemon 配置概览](https://docs.docker.com/engine/daemon/#configure-the-data-directory-location)

因此，下面这种单独修改不完整：

```json
{
  "data-root": "/www/docker-data"
}
```

它不能保证 `/var/lib/containerd` 的约 43G 被迁走，反而可能造成“Docker 看起来已经换盘，但系统盘仍持续增长”的错觉。Docker 官方也指出，containerd 使用独立于 Docker data directory 的存储路径，需要单独配置以避免填满根分区。[Docker containerd image store](https://docs.docker.com/engine/storage/containerd/#disk-space-usage)

### 2.3 containerd 的 `root` 与 `state` 不同

上游 containerd 运维文档定义：`root` 存放持久化数据，包括 snapshots、content、容器和镜像 metadata 以及插件数据；`state` 存放 sockets、PIDs、运行时状态、mount points 等重启后不应持久化的临时数据。[containerd upstream ops.md](https://github.com/containerd/containerd/blob/main/docs/ops.md#base-configuration)

所以建议只迁移持久化 `root`，例如：

```toml
version = 2
root = "/www/containerd-data"
# state 继续使用发行版默认值，例如 /run/containerd
```

不能通过手工移动或清理 containerd 的内部子目录来“瘦身”。上游文档把 `root` 和 `state` 目录都定义为 containerd 及插件的实现细节，并明确警告不要篡改，否则可能导致损坏或 bug。[containerd upstream ops.md](https://github.com/containerd/containerd/blob/main/docs/ops.md#base-configuration)

## 3. 与 longdao/sub2api 的边界

已知 longdao 侧存在独立运行时目录 `/www/longdao/runtime/docker`，sub2api 持久化数据位于 `/www/longdao/app-data`，并包含 PostgreSQL、Redis 等业务数据。本文不建议把这些目录重新组织成全局 Docker 目录：

- `/www/longdao/runtime/docker` 继续作为 longdao 专用 Docker daemon 的目录，实际 daemon 配置和 service unit 需现场核对。
- `/www/longdao/app-data`、PostgreSQL、Redis 是业务持久化数据，按 sub2api 自己的备份、停写和恢复流程管理，不等同于 Docker 镜像层或 containerd snapshots。
- SEP `/www/sep` 继续作为 SEP 应用、数据库、Redis、上传文件、知识库文件和备份的业务目录；不要把它作为 Docker 的 `data-root` 或 containerd `root`。
- 本策略只讨论 Docker/containerd 存储位置及其启动顺序，不移动 PostgreSQL/Redis 业务数据，也不修改 sub2api 的应用数据布局。

推荐使用彼此独立的目录，例如：

```text
/www/sep/runtime/containerd       # 系统 Docker 使用的 containerd root
/www/sep/runtime/docker          # 系统 Docker 使用的 data-root
/www/longdao/runtime/docker       # longdao Docker，保持独立
/www/longdao/app-data             # sub2api 业务持久化数据
/www/sep                          # SEP 业务与备份数据
```

目录名仅为策略示例。若系统 Docker 还承载其他项目，应将两条运行时路径改成该 daemon 的共享专用目录，不能放到某个项目目录下。正式执行前根据 service unit、权限、磁盘类型、面板依赖和备份方案确认；不要直接覆盖已存在的 `/www/longdao/runtime/docker` 或业务目录。

## 4. 推荐迁移顺序

### 阶段 A：只读盘点与回退准备

迁移前应完成并保存到受限目录的证据：

1. `findmnt /www`、`df -hT / /www`、`lsblk -f`、`blkid`、`cat /etc/fstab`。
2. `docker info`、`docker ps -a --no-trunc`、`docker volume ls`、`docker image ls --digests`、`docker system df -v`。
3. `systemctl cat docker.service containerd.service`，以及 `systemctl show -p FragmentPath,DropInPaths docker.service containerd.service`。
4. 检查是否存在第二个 Docker/containerd 实例、非默认 socket、面板生成的 unit 或自定义 `--data-root`/`--config` 参数。
5. 对 `/var/lib/docker`、`/var/lib/containerd` 和现有 daemon 配置做离线归档或文件系统级快照；至少保留原 `daemon.json`、containerd 配置、systemd drop-in、service unit 与校验清单。
6. 记录所有运行中的容器、镜像摘要、卷挂载、restart policy、端口和健康状态。不要把“镜像可重新 pull”当成容器配置和本地卷已备份。

在此阶段不改配置、不重启服务、不移动目录。

### 阶段 B：先演练，再生产停机迁移

如果有可用的临时磁盘或快照，先对同版本 Docker/containerd 做隔离恢复演练。至少验证：

- Docker 能看到原有镜像和容器；
- containerd snapshots 能被 Docker 正常使用；
- bind mount、named volume、网络、健康检查和 restart policy 仍符合预期；
- 不会读到 `/www/longdao/runtime/docker`、`/www/longdao/app-data` 或 `/www/sep` 的错误目录；
- `/www` 未挂载时，Docker/containerd 不会在空的系统目录中悄悄初始化一套新数据。

正式迁移必须设置维护窗口，停止会写入 Docker/containerd 的所有相关服务和容器。不要在 containerd 或 Docker 仍运行时直接复制/改写其内部目录；containerd 上游文档把这些目录视为实现细节，运行中操作会增加损坏风险。[containerd upstream ops.md](https://github.com/containerd/containerd/blob/main/docs/ops.md#base-configuration)

### 阶段 C：迁移 containerd `root`

以下是操作逻辑，不是可直接粘贴执行的无条件脚本；每一步都要检查退出码、目标挂载点和空间：

1. 确认 `/www` 是预期文件系统，并建立全新的、仅供系统 containerd 使用的目标目录，例如 `/www/sep/runtime/containerd`。
2. 先停止依赖 Docker 的工作负载，再按实际 unit 关系停止 Docker 和 containerd。保存停止前后 `docker ps -a`、`containerd` 服务状态和日志。
3. 使用保留权限、符号链接、硬链接、xattrs/ACL（如现场存在）的文件复制方式，把旧 `root` 完整复制到目标；复制期间不得有写入者。
4. 复制后做文件数量、总大小、关键目录和校验抽样；不要只比较 `du -sh`。目标目录必须位于已挂载的 `/www` 文件系统上。
5. 备份 `/etc/containerd/config.toml`，仅修改 `root`；不要顺便改变 snapshotter、runtime、registry、cgroup 或镜像存储 backend。
6. 为 `containerd.service` 和 `docker.service` 增加数据盘依赖，见第 5 节；执行 `systemctl daemon-reload`。
7. 启动 containerd，再启动 Docker；检查 `systemctl status`、`journalctl -u containerd -u docker`、`docker info`、镜像/容器/卷清单和业务 readiness。
8. 在至少一次服务重启或主机重启演练前，不删除旧 `/var/lib/containerd`。可以先重命名为受限的回退目录，但要确保回退方案仍可访问原路径。

Docker 官方文档没有给出“在线原地复制 containerd root”的通用迁移脚本；上述复制、校验、保留旧目录和分阶段启动属于本项目的保守运维建议，不能误标为 Docker 官方操作步骤。

### 阶段 D：迁移 Docker `data-root`

为满足后续部署统一使用数据盘，建议在同一维护窗口完成 `data-root` 迁移，但与 containerd `root` 分开配置、分步验证。这样 Docker 元数据、卷、容器日志等留在系统盘的部分也有明确的数据盘归属：

1. 先确认使用的是传统 driver，或确认 containerd image store 下哪些内容仍在 `/var/lib/docker`；不要把 `data-root` 当作 containerd 迁移的替代品。
2. 目标目录使用独立路径，例如 `/www/sep/runtime/docker`，不得复用 `/www/sep/runtime/containerd`、`/www/longdao/runtime/docker` 或业务目录。
3. 停止 Docker 后完整复制 `/var/lib/docker`，修改 `/etc/docker/daemon.json` 的 `data-root`，再按第 5 节配置挂载依赖。
4. 启动后检查 `docker info` 中 `DockerRootDir`、容器/镜像/卷清单、挂载和日志；确认旧目录未被误当成新空目录。

如果现场决定切换 storage backend（例如从 `overlay2` 改为 containerd image store），这已经超出“移动数据目录”的范围。Docker 官方警告，切换 backend 会暂时隐藏另一 backend 创建的镜像和容器；切换前应使用 registry 或 `docker save` 导出并按官方流程恢复，不能只复制目录。[Docker containerd image store](https://docs.docker.com/engine/storage/containerd/#enable-containerd-image-store-on-docker-engine)

## 5. systemd 挂载顺序与防止空目录启动

数据盘依赖必须覆盖所有读取 `/www` 的 daemon。systemd 官方定义 `RequiresMountsFor=/path` 会自动为访问该路径所需的 mount units 增加 `Requires=` 和 `After=` 依赖。[systemd.unit](https://www.freedesktop.org/software/systemd/man/latest/systemd.unit.html#RequiresMountsFor=)

建议为实际读取 `/www` 的 service 使用 drop-in，并在现场检查生成后的依赖：

```ini
# /etc/systemd/system/containerd.service.d/sep-data-mount.conf
[Unit]
RequiresMountsFor=/www/sep/runtime/containerd
```

```ini
# /etc/systemd/system/docker.service.d/sep-data-mount.conf
[Unit]
RequiresMountsFor=/www/sep/runtime/docker /www/sep/runtime/containerd
```

上面不是要求把所有路径都填进两个 unit：应只保留该 unit 实际使用的路径。例如系统 Docker 若只使用 `/www/sep/runtime/containerd` 和 `/www/sep/runtime/docker`，就不要把 longdao 路径写入系统 Docker。longdao Docker 应有自己的 unit/drop-in 和自己的 `RequiresMountsFor=`。

`RequiresMountsFor=` 同时表达“需要该挂载”和“启动顺序在挂载之后”。仅写 `After=www.mount` 而没有 `Requires=`，或只依赖 `local-fs.target`，不能充分表达目标目录必须可用的要求。systemd 也会为层级嵌套的 mount unit 自动建立依赖；`/etc/fstab` 生成的 mount unit 在 daemon reload/启动时参与依赖图。[systemd.mount](https://www.freedesktop.org/software/systemd/man/latest/systemd.mount.html)

本项目的 Docker 和 containerd drop-in 分别纳入 `deploy/standalone/docker.service.d/sep-data-mount.conf` 与 `deploy/standalone/containerd.service.d/sep-data-mount.conf`，并已安装到服务器。部署脚本的远端归档暂存目录使用 `/www/sep/tmp`，避免发布大归档落到系统盘 `/tmp`。

应用 drop-in 后必须验证：

```bash
systemctl daemon-reload
systemctl show -p Requires,After docker.service containerd.service
systemctl list-dependencies --all docker.service
systemctl list-dependencies --all containerd.service
findmnt /www
systemctl restart containerd docker
```

在真正重启前，先用 `systemctl start`/`restart` 的 dry-run 能力或隔离演练验证依赖；不要仅凭 unit 文件文本判断。重启/启动后再确认 `findmnt /www`、目标目录所在设备和 `docker info`，防止 `/www` 未挂载时在系统盘空目录创建新数据。

## 6. Docker 容器日志轮转

已知系统盘上的 Docker 目录只有约 3.9G，但日志可能随时间增长，必须把日志作为独立容量项监控。Docker 官方指出，默认 `json-file` 不做日志轮转，持续高输出可能耗尽磁盘；一般场景推荐 `local` driver，默认带轮转。[Docker logging drivers](https://docs.docker.com/engine/logging/configure/)

稳妥策略是先盘点现有容器的 driver，再决定新容器默认值：

```bash
docker info --format '{{.LoggingDriver}}'
docker ps -aq | xargs -r -n1 docker inspect \
  --format '{{.Name}} {{.HostConfig.LogConfig.Type}} {{json .HostConfig.LogConfig.Config}}'
du -xhd1 /var/lib/docker/containers 2>/dev/null | sort -h
```

如果保持 `json-file`，可为**新创建容器**设置轮转参数，例如：

```json
{
  "log-driver": "json-file",
  "log-opts": {
    "max-size": "20m",
    "max-file": "5"
  }
}
```

Docker 官方要求 `log-opts` 的数值和布尔值以字符串提供，并明确说明 daemon 默认配置只影响重启后新创建的容器；已有容器必须重建才会采用新配置。[Docker logging drivers](https://docs.docker.com/engine/logging/configure/)

也可以使用 `local` driver；官方文档说明其默认每容器保留约 100MB（20MB × 5 文件）并自动压缩，但这些文件只能由 Docker daemon 专用访问，不应使用外部工具直接改写。[local file logging driver](https://docs.docker.com/engine/logging/drivers/local/)

因此：

- 不要在 Docker 运行时使用 `truncate`、`rm` 或外部 logrotate 直接修改 `local` driver 文件。
- 不要因为修改 daemon 默认日志配置就认为现有 SEP/sub2api 容器已经轮转；要重建容器或在 Compose/创建参数中显式设置。
- 日志轮转是独立变更，建议在数据目录迁移完成、业务验证通过后再做，避免同时改变 storage backend、路径和日志 driver。

## 7. 验证清单

迁移后至少保存以下结果，作为回退和审计依据：

### 存储与服务

- `findmnt /www` 显示预期设备和文件系统。
- `df -hT / /www` 与迁移前容量一致，根分区没有因空目录启动重新增长。
- `systemctl is-enabled --quiet containerd docker` 的启用状态符合现状；不擅自改变 longdao unit。
- `systemctl is-active containerd docker` 为 active，`journalctl -b -u containerd -u docker` 无路径、权限、snapshotter 或数据库错误。
- `docker info` 的 backend、`DockerRootDir`、`LoggingDriver` 与迁移意图一致。

### 内容一致性

- Docker 镜像清单、digest、容器清单和容器配置与迁移前一致。
- containerd 目录中 snapshot/content/metadata 的数量和校验抽样符合迁移前记录；不直接编辑内部文件。
- named volumes、bind mounts、网络、端口、健康检查、restart policy 和 secrets/configs 可用。
- SEP `/www/sep`、sub2api `/www/longdao/app-data`、PostgreSQL、Redis 数据均未被本次 Docker 目录迁移改写。

### 业务与回退

- SEP、sub2api 的 readiness/health、关键页面和需要的模型中转连接通过。
- 业务日志仍可通过 `docker logs` 或既有日志系统读取。
- 至少一次 Docker/containerd 服务重启成功；若计划整机重启，先做维护窗口和控制台可达性确认。
- 原 `/var/lib/docker`、`/var/lib/containerd`、配置归档和校验清单仍保留，直到观察窗口结束。
- 回退只在停止相关服务后进行：恢复原配置、恢复原目录、确认 `/www` 数据盘依赖不会把服务导向半迁移目录，再启动并复核内容。

## 8. 观测窗口与回退触发条件

建议迁移后至少观察一个完整业务高峰，并持续记录 `/`、`/www` 的使用量、Docker/containerd 日志、容器重启次数和业务 readiness。出现以下任一情况，应停止继续清理旧目录并评估回退：

- Docker 或 containerd 看到空的镜像/容器列表；
- snapshotter、content store、metadata、权限或 mount 相关错误；
- `/www` 掉线后服务仍在系统盘生成新数据；
- SEP/sub2api 容器反复重启、挂载缺失、数据库/Redis 连接异常；
- 两个 Docker daemon 的目录或 socket 发生交叉使用；
- 业务数据目录 `/www/sep` 或 `/www/longdao/app-data` 出现非预期写入。

回退原则是“先停写、先停服务、恢复配置和原目录、再启动验证”。新 Docker/containerd 已产生的增量数据不能无条件丢弃；如已产生业务写入，应先完成业务数据备份和一致性评估，不能简单把旧目录切回去就宣称回滚完成。

版本和现场边界：

- Docker 官方文档称，Docker Engine 29.0 及以后**新安装**默认可能使用 containerd image store；升级安装可能继续使用 legacy graph driver。本文不把 Docker 版本或 backend 视为已知事实，必须用现场 `docker info` 核对。
- containerd `root`/`state` 的语义来自 upstream `ops.md`；具体发行版 unit、默认路径、插件和 snapshotter 可能不同，应以现场 `/etc/containerd/config.toml`、`systemctl cat containerd.service` 和软件包版本为准。
- Docker 官方资料说明了配置边界和日志行为，但没有提供适用于所有发行版、所有插件和第二个 Docker daemon 的“一键迁移脚本”。本文的停机、完整复制、校验、保留旧目录和分阶段启动，是基于官方边界制定的项目运维建议，执行前仍需现场演练。
- 本文没有执行服务器变更，也没有验证整机重启、掉盘恢复、特定 snapshotter、SELinux/AppArmor、加密盘或远程文件系统场景；这些场景应单独做恢复演练。
