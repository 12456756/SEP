# 企业充值记录退款功能开发文档

**文档日期**：2026-11-07
**适用端**：平台运营端企业详情页
**状态**：待开发

## 1. 背景与目标

平台运营人员需要在企业详情页的交易记录中处理企业充值退款。退款入口应贴近具体充值记录，避免运营人员在企业级余额上进行无法追溯的退款操作。

本期目标是提供一个足够简单、可审计的企业充值退款能力：运营人员只需选择一笔充值记录，退还该笔充值尚未使用且尚未退款的金额，或输入更小的部分退款金额。

## 2. 已确认的产品决策

1. **只有充值记录显示“退款”操作。**
   - `DEPOSIT`：显示“退款”。
   - `CONSUME`：不显示退款。已消费额度不支持在线退款。
   - `REFUND`：不显示退款，禁止二次退款。
   - 其他类型（人工调整、冻结、算力专款等）：不显示退款。
2. 退款入口放在平台运营端企业详情页的「交易记录」列表中，每条充值记录的操作列。
3. 退款金额支持两种快捷方式：
   - **退还全部可退余额**：默认选项，金额为该笔充值当前的可退款金额。
   - **退还部分金额**：运营人员输入金额。
4. 退款原因**选填**，不填写也可以提交。
5. 第一版不支持消费记录退款、部分消费冲正、退款审核流、退款申请单和复杂的多级状态机。
6. 第一版按平台现有钱包账本完成退款记账，不新增支付渠道原路退款流程；如后续需要支付宝原路退款，另行设计支付退款单和异步回调。

## 3. 核心业务规则

### 3.1 可退款金额

对某一笔充值记录 `D`，可退款金额按以下公式计算：

```text
该笔可退款金额 = 充值金额 - 该笔已退款金额
企业当前可退款余额 = max(0, balance - computeReservedCNY - frozenAmount)
最终可退款金额 = 向下取整到分(min(该笔可退款金额, 企业当前可退款余额))
```

其中：

- 充值金额取原始 `DEPOSIT` 交易金额的绝对值。
- 已退款金额为所有关联该充值记录的退款流水金额之和。
- 企业总余额取 `EnterpriseWallet.balance`，退款还需扣除算力专款 `computeReservedCNY` 和冻结资金 `frozenAmount`，不得挪用已保留资金或使用旧 `ComputeAccount.balance`。算力专款是总余额的子集，需要先按已有流程划回才能退款。
- 钱包保留 6 位小数用于算力结算，充值退款按分向下取整；不足 1 分的尾数保留在钱包内，不显示可执行的退款入口。详情接口、退款校验和退款后剩余可退金额使用同一计算逻辑。
- 当可退款金额小于或等于 0 时，该充值记录不显示“退款”，或显示为“已退完”且按钮禁用。
- 退款后企业钱包余额不能为负数。

示例：企业充值 ¥10,000，已消费 ¥3,000，当前余额 ¥7,000，则该笔充值最多可退 ¥7,000；不能退 ¥10,000。

### 3.2 退款金额

- 金额必须大于 0，最多保留 2 位小数。
- 不能超过该笔充值的未退款金额。
- 不能超过企业当前可用余额。
- 前端做即时校验，后端必须在事务内再次校验，不能信任前端传入的可退款金额。

### 3.3 退款原因

- 非必填，最大 200 个字符。
- 为空时，系统使用默认描述，例如“充值退款”。
- 有内容时写入退款流水 `description`，用于运营审计。

### 3.4 并发与幂等

- 退款操作必须在一个数据库事务内完成：读取钱包、计算已退款金额、校验余额、更新钱包、写入退款流水。
- 使用现有钱包版本号乐观锁；版本冲突时返回“余额已发生变化，请刷新后重试”。
- 提交按钮在请求处理中禁用，避免重复点击。
- 后端必须基于原充值交易 ID 重新汇总已退款金额，重复请求不能使累计退款超过原充值金额。

## 4. 前端交互

### 4.1 入口位置

页面：平台运营端 `/admin/enterprises/:id` 企业详情页。

交易记录表格新增“操作”列：

| 交易类型 | 操作 |
|---|---|
| 充值 | 退款 |
| 消费 | 无 |
| 退款 | 无 |
| 其他 | 无 |

按钮只对存在可退款金额的充值记录展示。

### 4.2 退款弹窗

标题：`充值退款`

展示内容：

- 原充值金额
- 已退款金额
- 当前可退款金额
- 企业当前余额
- 退款方式：
  - `退还全部可退余额 ¥x.xx`（默认）
  - `退还部分金额` + 金额输入框
- 退款原因（选填）

操作按钮：`取消`、`确认退款`。确认按钮在金额无效、余额不足或请求处理中禁用。

提交成功后：

- 关闭弹窗并提示“退款成功”。
- 刷新企业详情、余额和交易记录。
- 原充值记录的已退款金额和剩余可退款金额同步更新。
- 新增一条 `REFUND` 交易记录。

提交失败时直接展示后端错误信息，例如“该笔充值可退款金额已变化，请刷新后重试”。

## 5. 后端实现方案

### 5.1 复用现有模型

继续使用：

- `EnterpriseWallet`：企业余额和 `version` 乐观锁。
- `WalletTransaction`：充值和退款流水。
- `WalletTransactionType.DEPOSIT` / `REFUND`。

不新增退款申请表，不修改历史迁移。原充值交易通过退款流水的 `metadata.sourceTransactionId` 关联。

退款流水建议写入：

```ts
{
  type: 'REFUND',
  amount: amount.neg(),
  balanceBefore,
  balanceAfter,
  description: reason || '充值退款',
  createdBy: operatorId,
  metadata: {
    sourceTransactionId: depositTransactionId,
    refundKind: 'DEPOSIT_REFUND',
  },
}
```

本功能中的退款是企业钱包资金流出，因此退款流水金额使用负数；前端展示仍按“退款”语义显示为红色负向金额。现有用于取消订阅、释放预留金额的内部 `WalletService.refund()` 逻辑保持不变，不能直接复用其“增加余额”的方向。

### 5.2 Service

在 `backend/src/modules/wallet/wallet.service.ts` 增加专用方法，避免和现有内部退款混淆：

```ts
refundDeposit(params: {
  enterpriseId: string;
  depositTransactionId: string;
  amount: number;
  reason?: string;
  operatorId: string;
})
```

核心步骤：

1. 查询并校验原交易属于目标企业钱包，且类型为 `DEPOSIT`。
2. 汇总 `metadata.sourceTransactionId = depositTransactionId` 且 `type = REFUND` 的退款金额。
3. 计算原充值可退款金额和企业最终可退款金额。
4. 校验请求金额。
5. 按钱包版本号更新余额并扣减退款金额。
6. 写入 `REFUND` 流水，保存原充值 ID、操作人、原因和余额快照。
7. 返回新余额、退款流水和原充值剩余可退款金额。

建议使用现有 `assertActiveEnterpriseInTx`，冻结或非活动企业不能执行退款。

### 5.3 Controller

在平台运营端控制器增加：

```http
POST /admin/enterprises/:enterpriseId/transactions/:transactionId/refund
```

请求体：

```json
{
  "amount": 7000,
  "reason": "客户申请退还未使用余额"
}
```

`reason` 可省略或传空字符串。接口必须使用现有 JWT、平台运营角色守卫和 Zod 校验，并补充 Swagger `ApiOperation`、`ApiResponse`。

建议响应：

```json
{
  "success": true,
  "transactionId": "cl...",
  "refundAmount": 7000,
  "balance": 0,
  "remainingRefundableAmount": 0
}
```

## 6. 前端实现范围

建议修改：

- `web/src/app/(platform)/admin/enterprises/[id]/page.tsx`：交易记录增加操作列、退款弹窗和状态刷新。
- `web/src/features/admin/admin-api.ts`：增加退款请求方法和响应类型。
- `web/src/features/admin/use-admin.ts`：增加 `useRefundDeposit` mutation，成功后失效企业详情、企业列表和平台资金流水 query。

企业详情 API 的交易记录需要返回以下字段：

- `id`
- `type`
- `amount`
- `createdAt`
- `description`
- `refundedAmount`
- `refundableAmount`

`refundedAmount` 与 `refundableAmount` 可以在 Service 查询时根据退款流水聚合计算，不要求修改数据库表结构。

## 7. 测试与验收标准

### 7.1 后端单测

- 只有 `DEPOSIT` 原交易可以退款。
- `CONSUME`、`REFUND`、`ADJUSTMENT` 等交易退款时返回 400。
- 退还全部可退余额成功。
- 部分退款成功。
- 退款金额超过原充值未退款金额时拒绝。
- 退款金额超过企业当前余额时拒绝。
- 已消费金额不能被退回，余额不会变成负数。
- 退款原因为空时使用默认描述。
- 同一充值重复退款时，累计退款不超过原充值金额。
- 并发退款发生版本冲突时返回冲突错误，不能产生超额退款。

### 7.2 前端验收

- 充值记录显示“退款”，其他类型不显示。
- 弹窗默认选择“退还全部可退余额”。
- 原充值金额、已退款金额、可退款金额和企业余额展示准确。
- 原因不填可以成功提交。
- 成功后余额、交易列表和统计数据刷新。
- 已退完的充值记录不再提供可点击退款按钮。
- 金额非法、超过可退金额时有明确提示。

```bash
pnpm --dir backend test -- wallet.service.spec.ts
pnpm --dir web exec tsc --noEmit --incremental false
```

如修改 Prisma schema 或生成迁移，再按项目约定执行 `pnpm db:migrate` 和 `pnpm db:generate`；本方案默认不需要数据库迁移。

## 8. 明确不在本期范围内

- 消费记录退款或服务执行后的人工冲正。
- 支付宝/微信原路退款及支付平台异步回调。
- 退款审核、退款申请单、退款处理中状态。
- 自动按多笔充值拆分退款。
- 企业负余额、应收账款和退款后追缴。

后续若要支持原路退款，应在本方案稳定后独立增加支付退款单、退款状态机、回调幂等和财务对账，不直接扩展当前按钮逻辑。
